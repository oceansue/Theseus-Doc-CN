# 启动过程与执行流程

## 最初的汇编代码

Theseus 内核从引导加载程序手中接管控制权，最先执行的是*32 位保护模式*下的代码，对应于 `kernel/nano_core/src/boot/arch_x86_64/boot.asm` 中的 `start` 函数。
目前我们使用的 GRUB 被配置为传统引导加载程序（非 UEFI），Theseus 也期望由符合 *Multiboot2* 规范的引导加载程序来引导。
将来，我们打算增加对通过 UEFI 标准引导的支持，尤其是在那些没有传统 BIOS 的其他架构上。

在初始化一个非常简单的页表和其他若干硬件特性之后，汇编文件 `boot.asm` 会跳转到 `long_mode_start`，此时开始运行长模式（long mode）下的*64 位代码*。
接着，它会跳转到 `start_high`，这样我们就不会运行处于高半区的基内核镜像（关于[高半区内核](https://wiki.osdev.org/Higher_Half_Kernel)的更多信息请见此处）。
随后，我们建立新的全局描述符表（GDT）和段寄存器，最后带着正确的参数调用 Rust 代码入口点 [`nano_core_start()`](https://theseus-os.github.io/Theseus/doc/nano_core/index.html)。
在调用 `nano_core_start` 之后，那些汇编文件便不再被使用，而 `nano_core_start` 也应当永不返回。

## 最初的 Rust 代码：`nano_core`

`nano_core`（具体来说是 `nano_core_start()`）是 Theseus 中最先运行的 Rust 代码。
它执行一个非常精简的引导/初始化过程，其中完成以下职责：

- 初始化日志功能和一个基本的 VGA 文本显示，以便调试。
- 设置简单的 CPU 异常处理程序，以便捕获早期错误。
- 建立一个基本的虚拟内存环境。
    - 这会创建第一个也是唯一的虚拟地址空间，并把引导加载程序加载的所有节重新映射到这个新的单一地址空间中。
    - 重要的是，从这一刻起，Theseus 不再依赖来自引导加载程序的任何东西。
- 初始化 mod_mgmt 子系统，它会创建第一个 CrateNamespace，从而允许其他 crate 被动态加载。
- 加载并调用 `captain`，由它负责完成操作系统其余的初始化过程。

`nano_core` 相当通用且精简，几乎不需要改动。大部分与操作系统相关的配置和初始化都发生在 `captain` 中，因此改动通常应该在那里进行。

## 主要初始化例程：`captain`

`captain`"驾驭着 Theseus 这艘船"，也就是说，它包含了按正确顺序初始化所有其他子系统、并保证它们之间数据流正确的基本逻辑。

目前，Theseus 中只有一个 `captain` 实现（针对标准 x86_64 机器），它完成以下工作：

- 初始化 ACPI 和 APIC，以发现多核及其他硬件配置，
- 设置中断和异常处理程序，
- 设置基本的设备驱动程序，
- 派生事件处理线程，
- 初始化窗口管理器和图形子系统，
- 启动第一个用户应用程序，目前是一个单独的终端窗口。

最后，`captain` 必须启用中断，以便让系统调度其他任务。
随后它便进入一个什么都不做的空闲循环，该循环再也不会被调度器运行。

> 注意：将来，Theseus 会针对不同平台添加更多与体系结构相关的 `captain`。
