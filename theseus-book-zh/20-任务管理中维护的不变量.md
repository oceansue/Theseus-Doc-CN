# 任务管理中维护的不变量

Theseus 在任务管理方面强制维护了若干关键不变量（invariant），以便让编译器能够在整个任务生命周期中保障内存安全并防止资源泄漏。

所有任务生命周期函数都利用了同一组泛型类型参数。
这三个类型参数 `<F, A, R>` 上的 trait 约束是与任务相关的各项不变量的关键所在。

- F：入口函数的类型，即它的签名，包括参数和返回类型。
- A：传给入口函数 F 的那个参数的类型。
- R：入口函数 F 的返回类型。

## 不变量 1：派生新任务不得违反内存安全。

对于多个并发的用户态线程，Rust 本身已经保证了这一点，只要这些线程是用其标准库的线程类型创建的。
Theseus 没有使用标准库，而是提供了自己的任务抽象，从而克服了标准库的一个缺陷：它需要在语言之外（extralingually）迁就不安全的、平台相关的线程接口，例如 `fork()`。
Theseus 不提供 fork，因为众所周知它是不安全的，而且不适合单一地址空间（SAS）系统，
因为它会在语言之外复制任务上下文、状态和底层内存区域，却没有在语言层面反映出这种别名共享（aliasing）。

Theseus 的任务抽象以与 Rust 线程相似的方式保障安全性，并可视为对 Rust 线程的一种扩展。
用于派生新任务的接口（位于 [spawn](https://theseus-os.github.io/Theseus/doc/spawn/index.html) crate 中）要求明确指定入口
函数 `F` 的确切类型、其参数 `A` 的类型以及其返回类型 `R`，并满足以下约束：

1. 入口函数 F 必须只能运行一次，也就是说它必须满足 FnOnce trait 约束。
2. 参数类型 A 和返回类型 R 必须可以安全地在线程之间传递，也就是说它们必须满足 Send trait 约束。
3. 这三个类型的生命周期都必须长于任务本身的存续时间，也就是说它们必须拥有 'static 生命周期。

所有[任务生命周期管理函数](https://www.theseus-os.com/Theseus/book/subsystems/task.html#the-task-lifecycle)都是完全类型安全的，并且都用同一组泛型类型参数 `<F,A,R>` 进行参数化。
这既保证了类型信息在编译期可用，也保证了这些类型信息从头到尾（从派生到清理）贯穿任务生命周期各个阶段的*出处*（provenance）是一致的。
Theseus 借此让编译器能够在编译期静态地阻止那些不合法的任务入口函数——其参数、返回值或执行语义违反类型安全或内存安全。


## 不变量 2：在所有可能的执行路径上都必须释放任务的状态。

要释放任务状态，需要考虑一些特别之处，而不能只是简单地 drop 一个 Task 对象，这样才能防止资源泄漏，正如上一章所述。
任务清理的多个阶段各自允许释放的资源范围不尽相同，下面给出几个例子：

- 任务的栈会在栈展开期间被使用，因此只能在展开完成之后才能被清理。
- 已保存的执行 `Context` 可以在任务退出后被释放。
- 任务的运行状态（runstate）和退出值必须一直保留到它被收割为止。

[上一章](https://www.theseus-os.com/Theseus/book/subsystems/task.html#cleaning-up-tasks)所描述的任务清理函数展示了 Theseus 为确保在正常和异常执行路径下都完整释放任务状态和资源所付出的种种努力。
此外，如上所述，所有清理函数都用同一组 `<F, A, R>` 泛型类型参数进行参数化，
这对于实现可重启任务至关重要，因为可重启任务的失败处理函数必须知道入口函数、参数和返回类型的具体类型参数，才能重新派生出一个失败任务的新实例。

## 不变量 3：从任务入口函数可传递可达的所有内存，其存续时间都必须长于该任务。

尽管 Theseus 中的所有内存区域都由 `MappedPages` 表示，并借助生命周期不变量防止了释放后再使用（use-after-free），
但很难用 Rust 的生命周期来充分表达一个任务与它所访问的任意内存区域之间的关系。
Rust 语言没有、也无法指定一种基于任务的生命周期，例如 `&'task`，用来表明某个引用的生命周期与当前任务的生命周期绑定在一起。

此外，作为一个任务运行的 Rust 程序无法在代码中声明：其绑定到内存中对象的变量的生命周期与某个底层 `MappedPages` 实例绑定在一起，因为这些内存区域都隐藏在栈、堆或静态程序段（.text、.rodata 等）这类抽象之下。
即便可以做到，这也会非常不符合人体工学、极不方便，并使所有权机制失去意义。
例如，所有局部栈变量都必须被定义为借用引用，其生命周期派生自表示该栈的 `MappedPages` 对象的生命周期。

因此，为了维护这条不变量，我们转而建立一条清晰的所有权链：
每个任务都拥有包含其入口函数的 `LoadedCrate`，
而该 `LoadedCrate` 又通过 crate 元数据中按段（per-section）记录的依赖关系，拥有它所依赖的其他 `LoadedCrate`。
这样一来，凡是包含从某个任务入口函数可达的全部函数和数据的那片 `MappedPages` 区域，就得到了保证，
其存续时间一定长于该任务本身。
这避免了那种在所有程序变量上散布生命周期约束的糟糕做法，让 Rust 代码可以按照标准假设正常编写，即
栈、堆、数据段和代码段将永远存在。
