# Theseus 的理念与灵感

Theseus 是一个安全语言操作系统（safe-language OS），也就是说，它依靠 Rust 语言及其编译器所提供的类型安全与内存安全保证，来在任务（task）与组件之间实施保护与隔离。

正因如此，它放弃了硬件保护，这通常能带来更高的效率，因为可以省去切换特权模式和地址空间所产生的开销。

只有在所有应用程序都使用安全 Rust 编写时，这才能成立——安全 Rust 会阻止它们绕过任何基于类型的限制，从而避免造成非预期或未定义的行为。

## P.I.E. 原则

P.I.E. 原则是 Theseus 乃至我们其他许多系统软件研究工作中的指路明灯。
其核心思想是：计算目标有三大支柱，而硬件只应负责其中两个：
1. 性能（Performance）
2. 隔离（Isolation）
3. 效率（Efficiency）
传统上，系统软件设计者期望硬件同时提供这三者——高性能、强隔离以及高效率（低开销）。
我们认为硬件无法同时完全实现这三点。P.I.E. 原则主张，硬件*只*应负责性能与效率，而在提供隔离、安全性与保安性方面*不应扮演任何角色*（或只扮演极小的角色）。
隔离应当完全由软件负责。

我们有时也将其称为 **PHIS** 原则：**性能**交给**硬件**（**P**erformance in **H**ardware），**隔离**交给**软件**（**I**solation in **S**oftware）。

*但为什么呢？*

一方面，Meltdown 和 Spectre 等投机执行攻击表明，由硬件保障的隔离并不能像我们曾经认为的那样，保护内核数据免受不可信用户空间应用的侵害。闭源硬件（CPU 架构）的真实行为难以验证，甚至根本无法验证，因此我们转而依赖开源软件——操作系统、编译器、语言库等都可以接受审查，甚至可以进行形式化验证。

另一方面，Rust 这类现代语言能够在编译期确保类型安全与内存安全，而不必像传统的安全/托管语言那样，依赖低效的垃圾回收和透明的基于堆的对象管理所带来的开销。
因此，我们可以利用这些安全保证，确保编译出的代码不会破坏任务（task，即执行线程）与软件模块之间的隔离，而无需大量运行时检查。

Theseus 摆脱了对硬件提供隔离的依赖，彻底放弃了硬件特权级（x86 的 Ring 0 与 Ring 3 之分）以及多地址空间。
相反，我们在 Ring 0 上、于单一虚拟地址空间中运行所有代码，其中包括完全用安全 Rust 编写的用户应用程序。
这样既最大化了效率，又保留了保护能力，因为我们可以在编译期保证某个应用程序或内核组件无法破坏模块之间的隔离，从而使硬件特权级变得毫无必要。
Theseus 仍然使用内存管理单元（MMU）提供的虚拟内存转换，但仅仅是出于便利性和易于内存管理的考虑；直接为应用程序处理和分配物理内存，以及寻找大块连续的物理内存，往往既困难又低效。
