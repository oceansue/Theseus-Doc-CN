# 虚拟内存到物理内存的映射

要想真正地*使用*和*访问*内存，你必须把虚拟地址映射到物理地址。
你无法直接访问物理地址，因为 CPU 期望处理的是*虚拟*地址，这些虚拟地址会由内存管理单元（MMU）和其他内存控制器硬件自动翻译成物理地址。
此外，虚拟地址本身毫无用处；在把它映射到某个真实存在的底层物理地址之前，它没有任何内容，也没有任何用途。

内存映射需要建立页表并创建页表项，以 MMU 能够理解的方式表示从虚拟地址到物理地址的映射。
只要当前活动的页表中存在某个映射，你就可以通过访问映射到它的虚拟地址来访问真实物理内存中的内容。
访问内存不过是解引用某个特定虚拟地址上的指针；指针本质上就是带有类型的虚拟地址。

如果试图访问当前未被映射的虚拟地址，就会引发*缺页异常*（page fault），这是一种 CPU 异常，它会暂时中止正常的执行流程，以便让操作系统中的缺页异常处理程序尝试为这个未映射的虚拟地址建立合适的页表项。
利用缺页异常正是实现按需分页（on-demand paging）的方式；Theseus 目前并没有这样做，因为它违背了 [PHIS 原则](https://www.theseus-os.com/Theseus/book/design/idea.html#pie-principle)。

Theseus 的内存子系统为映射内存定义了三个关键类型：

- [`Mapper`](https://theseus-os.github.io/Theseus/doc/memory/struct.Mapper.html)：提供把虚拟内存映射到物理内存的函数，这些函数会创建并返回 MappedPages 对象。
- [`PageTable`](https://theseus-os.github.io/Theseus/doc/memory/struct.PageTable.html)：一个顶级页表，它拥有页表的根帧，以及一个使用该页表帧来创建新页表项的 Mapper 实例。
    - 它会自动解引用为 Mapper，因此可以在 PageTable 对象上直接调用所有 Mapper 的函数。
- [`MappedPages`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html)：一个表示虚拟地址连续的一段页的对象，这些页已被映射到物理帧上，并且只有唯一的独占所有者。

`Mapper` 类型实现了 Theseus 中映射内存的两个核心函数：

1. map_allocated_pages()：把特定范围的 AllocatedPages 映射到若干帧上，这些帧由系统按需分配，物理地址是随机选取的。
    - 适用于这样的情形：你拥有一些虚拟页，只想把它们用于一般用途，并不关心映射到的是哪些物理内存。
2. map_allocated_pages_to()：把特定范围的 AllocatedPages 映射到特定范围的 AllocatedFrames 上。
    - 适用于你需要访问某个硬件设备或某段位于特定物理地址的内存的情形。

细心的读者会注意到，你*只能*把一段拥有独占所有者的 `AllocatedPages` 映射到一段拥有独占所有者的 `AllocatedFrames` 上。
你不能简单地把一个裸虚拟地址或页映射到一个裸物理地址或帧上；它们必须先从相应的分配器处专门申请得到，然后通过当前活动的页表进行映射。
这正是 Theseus 确保在编译期就能保证访问*任意*内存区域都是安全的方法的一部分。

## `MappedPages` 类型

[`MappedPages`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html) 类型表示一段虚拟地址连续的页，这些页*在静态意义上得到保证*已被映射到真实的物理帧上（这些物理帧未必连续）。
一个 `MappedPages` 实例包含以下内容：

- 它所拥有的、并且当前已映射到的 AllocatedPages 范围
- 映射时使用的权限标志，例如是否只读、是否可写、是否可被缓存（cacheable）等
- 它映射时所在的根页表，用于额外的安全性与健全性检查

`MappedPages` 是 Theseus 中表示和访问已映射内存的根本且唯一的途径；它是[栈](https://theseus-os.github.io/Theseus/doc/stack/struct.Stack.html)、堆以及其他任意内存区域（例如设备 MMIO 和已加载的细胞（cell））的底层表示。

### 编译期的不变量与安全性保证

`MappedPages` 的设计让编译器的类型系统能够强制实施以下关键不变量，从而把 Rust 的内存安全检查扩展到*所有*操作系统已知的内存区域，而不仅仅是编译器已知的栈和堆。

1. 从虚拟页到物理帧的映射必须是一对一的，即双射的。
    - 在整个系统范围内，每个 Page 只能映射到一个 Frame，每个 Frame 也只能被一个 Page 映射。
2. 一段内存区域必须恰好被解除映射一次，并且只有在不再存在任何未完成的引用之后才能解除映射。
3. 一段内存区域不能在其边界之外被访问。
4. 一段内存区域只有以可变或可执行方式映射之后，才能以可变或可执行的方式被引用。

这些不变量与 Rust 既有的内存安全规则完美契合，例如防止出现多个无效别名（别名 XOR 可变性）、越界访问、释放后使用与重复释放，以及被禁止的可变访问。

### 如何使用 `MappedPages`

`MappedPages` 的一个关键特性是它的"访问方法"（access methods），它们让调用者能够安全地把底层已映射的内存区域重新解释为某种特定的类型。
对无类型内存进行重新解释是任何内存管理子系统都必不可少的能力；Theseus 提供了完全安全的接口来实现这一点，而现有的操作系统则做不到。
重新解释型的类型转换有时也被称为"结构体覆盖"（struct overlay），因为你是在一段已有的内存区域之上覆盖一个结构体。

| 访问方法名称 | 返回类型 | 说明 |
| --- | --- | --- |
| [`as_type()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.as_type) | `&T` | 返回一个泛型类型 `T` 的不可变引用，该对象起始于内存区域中某个特定的偏移量处。 |
| [`as_type_mut()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.as_type_mut) | `&mut T` | 与 `as_type()` 相同，但返回的是*可变*引用。 |
| [`as_slice()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.as_slice) | `&[T]` | 返回一个*切片*（动态大小数组）的引用，其中包含 `N` 个类型为 `T` 的元素，起始于某个特定的偏移量处。 |
| [`as_slice_mut()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.as_slice_mut) | `&mut [T]` | 与 `as_slice()` 相同，但返回的是类型为 `T` 的切片的可变引用。 |
| [`LoadedSection::as_func()`](https://theseus-os.github.io/Theseus/doc/mod_mgmt/struct.LoadedSection.html#method.as_func) | `& <impl Fn(...)>` | 返回一个函数的引用，该函数位于某个 `LoadedSection` 的内存区域之内，该区域必须是一个可执行的 `.text` 节。 |

这些访问方法保证了前文所述的 `MappedPages` 类型的各项不变量。

1. 泛型类型 T 的大小必须在编译期已知（T: Sized），它加上偏移量之后不得超过内存区域的边界。
    - 对切片来说同样如此：大小已知的类型 T: Sized 的元素个数加上偏移量，不得超过该区域的边界。
2. 如果请求的是可变引用，那么底层内存区域必须是以可写方式映射的。
    - 对函数和可执行的内存区域而言同样如此。
3. 这些方法都会返回所请求类型或切片的引用，其中返回引用（&T）的生命周期依赖于 MappedPages 对象的生命周期，以便在静态意义上防止释放后使用的错误。
    - 你无法从一个底层的 MappedPages 内存区域中获得类型 T 的一个所有权实例，因为那样做会切断类型 T 与底层内存映射存在性之间的语义联系。

相比之下，其他操作系统通常在内存映射操作中直接返回裸的虚拟地址值，然后你必须不安全地把它们强制转换成你选定的带类型指针。
使用裸地址时，没有任何生命周期方面的保证来确保在这些虚拟地址被使用期间映射一直存在。
因此，Theseus 在编译期就消除了在裸虚拟地址被解除映射之后继续使用它、从而轻易导致不安全的未定义行为的可能性。

更多细节请参见 OSDI 2020 的 Theseus 论文，或 Kevin Boos 的学位论文，二者均可[在此获取](https://www.theseus-os.com/Theseus/book/misc/papers_presentations.html#selected-papers-and-theses)。

`MappedPages` 类型还提供了其他一些便利的工具方法：

- [`remap()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.remap)：修改这些虚拟页的权限标志，它们仍然映射到相同的物理帧。
- [`merge()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.merge)：把多个连续的 MappedPages 对象合并为一个。
- [`unmap_into_parts()`](https://theseus-os.github.io/Theseus/doc/memory/struct.MappedPages.html#method.unmap_into_parts)：解除对该内存区域的映射，并重新取得其组成部分（AllocatedPages 等）的所有权，以备将来使用。
    - 如果不调用此方法，MappedPages 对象会在被 drop 时自动解除映射，其组成部分也会被释放以备将来使用，
但这一切都会在幕后发生，你无法直接访问它们。
- 你也可以调用来自 [`PageRange`](https://theseus-os.github.io/Theseus/doc/memory_structs/struct.PageRange.html) 的任何方法。

## 释放帧

释放虚拟页非常简单，因为 `AllocatedPages` 范围直接存储在 `MappedPages` 对象中并由其拥有，所以只需在这些页被 drop 之后将其释放即可。

然而，释放一段 `AllocatedFrames` 就困难得多，因为一段虚拟地址连续的页中，每一页很可能被映射到互不相同、不连续的若干帧集合上。
这意味着我们可能不得不释放许多组 `AllocatedFrames`，极端情况下每一页都要对应一组。

在现有的操作系统中，没有办法简单而迅速地确定哪些帧映射到了哪些虚拟页；这需要一种从 `1` 个帧到 `N` 个页的*反向映射*，而维护这样的映射开销大得令人望而却步。
因此，操作系统内核通常会在空闲的 CPU 上周期性地运行一个"垃圾回收"线程，扫描各张页表以确定哪些帧可以被回收。

不过，Theseus 的设计极大地简化了回收并释放未使用物理帧的过程。
单一地址空间的设计加上得到保证的双射（一对一）映射，意味着一个帧只会被某一个页*独占地*映射；当那个页不再映射到该帧时，这个帧就可以被释放了。
我们把这称为独占映射（exclusive mappings），它们由几个 crate 协同实现：

1. 在 [`page_table_entry`](https://theseus-os.github.io/Theseus/doc/page_table_entry/index.html) crate 中，当帧被解除映射时，会创建一个 [`UnmapResult`](https://theseus-os.github.io/Theseus/doc/page_table_entry/enum.UnmapResult.html)，其中可能包含一组 [`UnmappedFrames`](https://theseus-os.github.io/Theseus/doc/page_table_entry/struct.UnmappedFrames.html)。
    - 其中最值得关注的主要函数是 [`PageTableEntry::set_unmapped()`](https://theseus-os.github.io/Theseus/doc/page_table_entry/struct.PageTableEntry.html#method.set_unmapped)。
2. 借助强类型安全，[`frame_allocator`](https://theseus-os.github.io/Theseus/doc/frame_allocator/index.html) 能够把一组 UnmappedFrames 当作一个可信的"令牌"来接受，它表明其中包含的帧不可能仍被任何页映射。因此可以安全地释放它们。
    - 释放过程是无缝完成的，因为一个 UnmappedFrames 对象可以被转换成一个 AllocatedFrames 对象，[详情与源码参见此处](https://www.theseus-os.com/Theseus/doc/frame_allocator/fn.init.html#return)。
---

> **译注（原书脚注）**：这里假设 CPU 处于标准模式，例如启用了分页的保护模式或长模式。内存管理单元（MMU）是可以被禁用的，禁用之后虚拟地址不复存在，可以直接使用物理地址；但 Theseus（以及绝大多数其他操作系统）都不会禁用 MMU。
