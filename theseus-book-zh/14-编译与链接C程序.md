# 编译与链接 C 程序

> *警告：* 在 Theseus 之上构建 C 程序的支持尚处于实验阶段，随时可能发生变化。

目前，我们使用一种自定义的"分离式"（split）链接方式，它在编译时完全静态，*并且*在运行时部分动态。

## 1. 构建时的完全静态链接

这一过程可以分解为以下几个步骤：

1. 把 tlibc 作为一个标准 Rust crate 编译成一系列目标文件，
2. 把这些与 tlibc 相关的目标文件合并或链接为单个归档文件或目标文件，
3. 编译基本的 C 程序，例如 dummy.c，
4. 将该 C 程序与预构建好的 tlibc 目标文件进行静态链接，生成一个独立的可执行文件。

前两个步骤已在[前文](https://www.theseus-os.com/Theseus/book/c/tlibc.html)中描述过；后两个步骤将在下文说明。

为了构建一个 dummy C 程序并将其链接到 tlibc，目前调用 `gcc` 时需要若干参数，用以定制编译器的行为以及它对 `ld` 链接器的使用方式。关键参数如下所示，并附有说明：

```sh
x86_64-elf-gcc                             \
    -mno-red-zone -nostdlib -nostartfiles  \
    -ffunction-sections -fdata-sections    \
    -mcmodel=large                         \
    -Wl,-gc-sections                       \
    -Wl,--emit-relocs                      \
    -o dummy_works                         \
    path/to/crtbegin.o                     \
    dummy.c                                \
    path/to/tlibc.o                        \
    path/to/crtend.o
```

最重要的参数是：

- -mno-red-zone、-mcmodel=large：与 Theseus 在 Rust 侧的编译器配置保持一致，使 C 代码能够正确调用 Rust 代码。
- -Wl,--emit-relocs：在 ELF 可执行文件中（.rela 节）包含关于链接器所执行的具体重定位操作的细节。

执行完上面的 gcc 命令之后，我们就得到了一个独立的可执行 ELF 文件 `dummy_works`。

## 2. 运行时的部分动态重链接

ELF 可执行文件 `dummy_works` 可以立即在 Theseus 之上加载并执行，但它不一定能正常工作、按预期运行。
这是因为它是完全静态链接的，也就是说，该可执行文件中包含了与内存中已加载的 Theseus crate 实例（细胞，cell）里相同的数据节和函数节的重复副本。

最重要的是，这些数据节代表着系统范围的单例状态（Rust 中的 `static` 变量），它们*已经被初始化*，并且正处于所有其他 Theseus 组件的活跃使用之中。
因此，打包进可执行文件中的那些数据实例*尚未被初始化*，无法被安全地使用。
使用这些节会导致本应是系统范围单例的数据出现多个副本；这对大多数 Theseus 组件来说都是坏消息，例如帧分配器（frame allocator）的系统范围空闲物理内存列表。

为了解决这个问题，我们会重新执行（覆盖）可执行 ELF 文件中的所有重定位，使其指向*已经加载进 Theseus 的既有节*，而不是可执行文件自身中那些新的、未初始化/未使用的节。
这只适用于 Theseus 中已经存在的节；当然，对于该可执行文件所独有的新节，其中的引用会保持原样。
重定位信息通过上文所示的 `--emit-relocs` 链接器参数，以标准 `.rela.*` 节的形式编码进 ELF 文件本身。

这一过程目前由 `loadc` 应用程序执行；它还负责加载 ELF 可执行文件的段（program headers，程序头）并管理它们的元数据。
