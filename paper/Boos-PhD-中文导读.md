## 摘要（Abstract）

状态管理已成为现代操作系统中一个难以解决的问题，其原因在于操作系统庞大的规模与复杂度。尽管人们一直努力对操作系统进行清晰的模块化，状态的传播与管理不善仍然是许多计算目标（例如系统演化与容错）的重大障碍。我们识别出此类障碍的根本原因是**状态溢出**（state spill），即一个软件实体的状态在处理与另一实体的交互之后发生了持久性改变的现象。我们系统性地研究了状态溢出在现有操作系统中的存在与表现形式，发现它深深植根于底层的操作系统内核以及 Android 系统服务这类框架级组件之中。

为此，我们提出 Theseus——一个用 Rust 从零开始编写的实验性操作系统，它重新思考操作系统的整体结构，并把状态管理作为一等设计关注点。Theseus 有两项主要贡献。第一，其操作系统结构由大量微小的、类似细胞的实体构成，这些实体具有清晰的、运行时持久的边界，全部动态加载与链接，并且在彼此交互时不为对方保存状态。第二，其语内（intralingual）设计与实现利用现有的语言级机制来实现操作系统功能，使编译器能够强制执行关于操作系统语义的不变量，从而让我们可以把资源记账的职责从操作系统转移到编译器，大幅缩减操作系统必须维护的状态集合。Theseus 的结构、语内设计与状态管理原则共同促成轻松且任意的在线演化（live evolution）、系统灵活性，以及通过故障恢复获得的可用性——即使对核心操作系统组件也不例外。

## 核心贡献

1. **提出并系统化"状态溢出"（state spill）概念**：给出基于"软件实体 + 事务（transaction）"的系统模型与形式化定义，证明状态溢出是阻碍系统演化、容错、灵活性等计算目标的根本原因，并指出它是相对性的概念（取决于实体粒度与事务的时间划分）。
2. **状态溢出的定性分类与定量分析**：归纳出四种典型模式——间接层、多路复用器、分发器、实体间协作，并以 Linux 进程抽象、VFS、MINIX 3 用户态服务器、X Window 等为例逐一剖析其危害；同时开发 STATESPY 工具，用运行时与静态分析相结合的反馈环自动检测 Android 系统服务中的状态溢出。
3. **Theseus 操作系统的全新结构**：以"细胞（cell）"作为唯一实体形态，所有实体边界运行时持久、全部动态加载链接，配合 `CellNamespace` 符号表与双向依赖元数据；仅用极小的 `nano_core` 静态引导，其余部分皆按需加载。
4. **语内设计（intralingual design）方法**：让操作系统执行环境与 Rust 的运行时模型完全匹配（单一地址空间 SAS、单一特权级 SPL、单一分配器），把资源特定的不变量归并进编译器不变量，用无损接口（如 `map()`）保留语言层上下文，从而把资源记账职责从 OS 转移给编译器。
5. **三大计算目标的实现机制**：细胞交换实现任意粒度的在线演化（可像 git 提交一样更新内核组件）；多级故障恢复（栈展开 → 可重启任务 → 重初始化静态数据 → 替换损坏细胞）实现可用性；多 `CellNamespace` 并存实现灵活的"系统人格"。
6. **实验验证**：故障注入实验中 Theseus 从 69% 的已显现故障中恢复（含微内核级实体），并与 MINIX 3 做了细致对比；微基准表明语内设计在内存映射上更快，任务与堆管理有轻微到中等的开销（第 9 章内容，据目录与图表说明概括）。

## 各章要点

**第 1 章 引言（pp. 1–5）**（已读 pp. 1–4）
现代操作系统庞大而复杂，像一团难以解耦的组件之网；以往模块化努力忽视了状态溢出，把状态管理当成事后考虑。作者提出核心研究假设：**从根本上重新设计操作系统以避免状态溢出，将使系统更容易演化、更容易从故障中恢复；而充分利用现代语言与编译器的力量可以进一步加强这一点**。论文分两部分：前半部分（第 2、3 章）是对现有系统状态溢出的定性与定量研究（含 STATESPY 工具）；后半部分（第 4–7 章）是 Theseus 的设计与实现。Theseus 的所有实体存在于单一地址空间（SAS）与单一特权级（SPL）中，靠语言提供的类型与内存安全而非硬件保护实现隔离（受 Singularity 等安全语言 OS 启发），并确立三条设计原则：P1 要求所有实体具有清晰且运行时持久的边界；P2 最大化语言与编译器的力量；P3 让实体免于状态溢出。作者引用 Microsoft、Chromium、Mozilla 的大规模研究指出约 70% 的严重缺陷是内存安全缺陷，并强调 Theseus 的语内设计"超越安全性"，让编译器能静态检查资源释放等 OS 语义不变量。章末脚注解释了书名典故：忒修斯之船——如果木船的每一块木板都被逐渐替换，它还是原来那条船吗？（这正是系统在线演化的隐喻。）

**第 2 章 状态溢出概述（pp. 6–13）**（已读 pp. 6–12）
本章给出状态溢出的正式定义：实体 B 的状态在处理来自实体 A 的交互之后发生了**持久性改变**，由此 B（"服务器"）与 A（"客户端"）被不可撤销地紧耦合，导致 B 无法被替换或修改。作者用嵌套抽象层次中的"软件实体"与具有 IPC 语义的"事务"建模一切实体间通信（函数调用、系统调用、中断、信号均可视为事务），并定义了事务的三条边界情形（被中断即未完成；永不返回的发散事务与状态溢出无关；处理失败等同成功完成）。与传统的静默（quiescence）定义不同，本章用"活跃/非活跃"刻画实体：只有在实体间事务完成时才算非活跃。实体状态被限定为其作用域内程序变量及其取值，并排除临时状态（生命周期不超过当前事务的局部变量），从而具有马尔可夫性，便于静态与动态分析。状态溢出是**相对的**：它同时取决于空间粒度（整台计算机 → 应用 → 模块/类 → 函数）与时间粒度；过粗或过细都不可行，作者选择"模块级"中等粒度——在 Theseus 中即为细胞（cell），并指出 RESTful 架构可看作最粗粒度上避免状态溢出的尝试。

**第 3 章 现有系统中的状态溢出分析（pp. 14–40）**（已读 pp. 14–21，其余据目录与插图说明概括）
作者把状态溢出归纳为四种设计模式：（1）**间接层**在两个抽象层次之间转换时积攒客户端状态，例如 Linux 进程抽象导致状态溢出到内核的 `task_struct`（使进程迁移几乎不可行）、VFS 的 `file` 结构被底层 I2C 驱动透明修改（一种"欺骗性"的隐式状态溢出）、MINIX 3 用户态调度器 SCHED 通过 `sys_schedctl` 把进程参数泄入内核（阻碍在线更新与热替换）；（2）**多路复用器**为多个客户端复用同一资源而保存每客户端状态，如进程管理（`fork` 创建的进程表项、驱动设置的阻塞标志）与窗口管理（X server 保存客户端窗口与内容、窗口管理器维护 Z 序），其中 X server 的共享缓冲区甚至可被恶意客户端利用造成任意内存写；（3）**分发器**因保存客户端注册的回调引用而溢出；（4）**实体间协作**要求非正交状态同步。这些溢出分别破坏进程迁移、故障隔离、容错、热替换与安全性。3.2 节介绍 STATESPY 工具：运行时分析 + 静态分析 + 反馈环的自动化检测（未逐页阅读）；3.3 节把该工具用于 Android 系统服务，证明状态溢出在 Android 中普遍存在，并区分主要与次要状态溢出，含 Flux 案例研究（未逐页阅读）。

**第 4 章 Theseus：概览与设计原则（pp. 41–44）**（已读）
Theseus 是用 Rust 从零编写的实验性 OS，既不是宏内核、微内核、外核也不是 multikernel，但兼取各家之长：像宏内核一样在单一地址空间里运行全部代码以获得性能，避免了宏内核"实体边界在运行时消失"的问题；不像微内核那样把实体边界绑定到硬件进程，也不把内核本身编译成不可分割的代码块；比 Library OS 的 personality 更灵活且无需地址空间切换；与 Barrelfish、K2 等"按硬件结构划分"的系统不同，Theseus 的实体结构与硬件布局无关。本章还给出 Rust 背景知识：所有权模型（值有唯一所有者、作用域结束时由编译器插入析构调用）、仿射类型、借用检查器、"别名 XOR 可变性"原则，以及 Theseus 虽不用标准库但使用 `core` 与 `alloc`（含 `Arc`）。

**第 5 章 运行时持久实体的结构（pp. 45–50）**（已读）
本章落实设计原则 P1。Theseus 的每个实体都是一个**细胞（cell）**（与 Rust 的 `cell` 类型无关，见原书脚注）：实现时是 Rust crate，编译时是单个目标文件，运行时是一组带分节边界与依赖元数据的已加载内存区域——三个阶段形态一致，给开发者与系统自身提供统一的 OS 视图。运行时 Theseus 按需动态加载并链接所有细胞：解析目标文件、加载各节（`.text`/`.rodata`/`.data`/`.bss`）、重定位、递归加载缺失依赖、把公开符号加入符号表。每个细胞的元数据记录其各节的大小、内存位置（以 `MappedPages` 内偏移表示）、出向依赖与入向被依赖者（双向、按节记录）；全部已加载细胞构成 `CellNamespace`，即一个真正的命名空间与系统符号表。SAS/SPL 架构带来"完备性"：从应用到核心内核组件都可观察为细胞，因而单一机制"细胞交换"可统一适用于任何实体，并支持跨层联合演化。5.2 节讨论细胞粒度：Theseus 拒绝 Rust 的子模块嵌套（编译后边界丢失），把子模块提升为独立 crate 并按子系统分目录，取"足够小"与"避免过多循环依赖"之间的平衡；实体与执行上下文（任务）解耦，可以在不杀死任务的情况下替换其依赖的细胞。5.3 节介绍 `nano_core`：链接阶段被拆分，未链接的目标文件直接放入 OS 镜像，唯一静态链接的"基础内核" `nano_core` 只含引导所需功能（比 KeyKOS 的 nanokernel 还小，符合 Liedtke 的最小化原则），引导完成后它自身也被动态加载的细胞逐个替换并卸载，从而满足"所有细胞边界运行时持久"的要求。

**第 6 章 语言之力（pp. 51–69）**（已读 pp. 51–58；6.3.2、6.3.3 未逐页阅读）
本章落实设计原则 P2，定义**语内设计**：让 OS 执行环境匹配语言的运行时模型，并在语言的强静态类型系统之内实现 OS 语义；与之相对的是依赖硬件特性与运行时检查的"语言外（extralingual）"方法。语内设计带来三大好处：编译器接管资源管理从而减少 OS 必须维护的状态、把语义错误从运行时失败提前为编译期错误、编译器的安全检查无缝覆盖从应用到底层内核（现有安全语言 OS 在安全代码与其 unsafe 黑盒核心之间仍存在鸿沟）。6.1 节说明运行时模型匹配：SAS（保证一对一虚物映射）、SPL（没有其他执行模式）、单一分配器实例。6.2 节阐述两个手段：把资源特定不变量**归并**进编译器不变量（如用 `Arc` 共享资源，把"对象在所有使用者结束前不得释放"变成通用不变量），以及使用**无损接口**——跨越接口不得丢弃类型、生命周期、所有权等语言层上下文，且该上下文的来源（provenance）必须可静态验证（系统调用因要把参数压平为整数而"有损"）。作者还实现了一个从零编写的栈展开器（unwinder）：所有清理逻辑写在 drop 处理器中，由编译器决定"何时"触发清理，既保证资源不泄漏，也能在栈展开时释放锁从而预防死锁；Theseus 禁止 OS 从语言脚下撤销单个资源，只能以任务粒度杀死并展开，从而避免双重释放与 use-after-free。6.3.1 节以内存管理为例：`MappedPages` 类型是 Theseus 中映射与访问内存的唯一方式，其 `map()` 接口只接受独占拥有的 `AllocatedPages` 与 `AllocatedFrames` 并**消耗**它们，静态保证虚拟页到物理帧的双射映射不变量（M.1），使一切共享都必须走语言级机制；`as_type`/`as_slice` 的边界检查则把越界访问挡在类型层。任务管理与任务间通信通道两个子系统在 6.3.2、6.3.3 节展开（未逐页阅读）。

**第 7 章 Theseus 中的状态管理（pp. 70–75）**（未逐页阅读；据目录、图 7.1 说明与其他章节的引用概括）
本章落实设计原则 P3，提出**不透明导出**（opaque exportation）：服务器实体向客户端只导出进度状态而不再为客户端保存状态，从而实现无状态通信、解耦客户端与服务器（图 7.1 对比了传统封装式模块化与 Theseus 的方式）。7.1 节讨论如何避开常见的易溢出抽象以及容纳多客户端状态；7.2 节讨论 Theseus 中特殊状态（如静态/全局状态）的管理，并给出多个"因语内性而免于状态溢出"的例子。

**第 8 章 实现可演化性、可用性与灵活性（pp. 76–85）**（已读 pp. 76–82）
核心演化机制是**细胞交换**（cell swapping）：用 N 个新细胞替换 O 个旧细胞（O 与 N 不必相等），分四阶段——(i) 把新细胞加载进一个全新的空 `CellNamespace`（隔离的链接环境，避免误链到旧细胞）；(ii) 双向验证依赖：新细胞须满足旧细胞承担的所有依赖，新细胞的依赖也须被现有细胞满足；(iii) 重定向：改写依赖旧细胞的细胞之重定位项与元数据、更新栈上引用，必要时做状态转移；(iv) 原子地把新细胞移入现有 `CellNamespace` 并移除旧细胞及其符号。作者实现了一条"像 git 提交一样"的在线演化流水线：向仓库提交 → 构建服务器重编译 → 生成演化清单（evolution manifest，增广的 diff）→ 通知 Theseus 内的演化客户端下载并应用。运行时持久的细胞边界、无溢出设计与细胞元数据分别简化了细胞可移除性、状态转移与依赖检查；转移函数（transfer functions）利用 Rust 的 `Into` 等 trait 与过程宏自动生成，把转换失败提前为编译错误，但当前依赖相邻版本之间演化，且无法覆盖汇编代码中的语言外用法（上下文切换与 VESA 检测是仅有的两处）。8.2 节讲可用性：故障隔离靠栈展开（甚至能清理应用提供的资源），故障恢复采用逐级升级的多阶段策略——容忍（展开并清理失败任务）→ 用 `spawn_restartable()` 重启可重启任务 → 重新初始化细胞的静态数据区 → 用细胞交换把损坏细胞替换为新加载的实例 → 全部失败才重启整机；系统维护全局故障日志以检测复发故障。8.3 节（未逐页阅读）介绍通过并存的多个 `CellNamespace` 共享任意数量的细胞来构建不同的系统"人格"（图 8.1）。

**第 9 章 评估（pp. 86–104）**（未逐页阅读；据目录、插图与表格清单概括）
本章通过案例研究验证三大目标：9.1 节演示对任务间通信通道、调度器/运行队列、网络更新客户端与以太网驱动、APIC 子系统等核心组件的在线演化，并给出各阶段耗时（仅中间两步可能需要系统暂停）；9.2 节给出故障恢复测量——在以任意内存损坏模拟硬件故障的注入实验中，Theseus 从 69% 的已显现故障中恢复（表 9.1）、记录了恢复停机时间（表 9.2），并与 MINIX 3 对比微内核级实体的恢复能力；9.3 节量化语内性与无溢出设计的代价与收益——`MappedPages` 映射/重映射/取消映射 4 KiB 页耗时恒定且略优于传统红黑树 VMA 方案（图 9.2）、从任务结构中移除运行队列状态的代价很小（图 9.3）、语内堆记账带来一定开销（表 9.3）、LMBench 微基准与 Linux 的对比见表 9.4。

**第 10 章 相关工作（pp. 105–113）**（未逐页阅读；据目录概括）
从四个方向梳理相关工作：状态溢出（10.1）、操作系统结构与整体设计（10.2）、操作系统组件的在线更新（10.3）、容错操作系统（10.4）。

**第 11 章 讨论与局限（pp. 114–122）**（已读 pp. 114–119）
作者坦率讨论了多项局限。**unsafe 代码**在底层内核中不可避免（编译器没有硬件语义模型），作者区分"无害的（innocuous）"与"传染性的（infectious）"unsafe——后者才可能破坏数据隔离——并开发了编译器插件自动检查 unsafe 块中地址的可达性与类型安全（内联汇编仍需人工白名单）。**故障恢复不完整**：panic 位置编译期可知、展开完美工作，但 CPU 异常可能发生在任意指令处，而 LLVM/Rust 不支持异步展开表（asynchronous unwind tables），故当前栈帧的局部变量可能未被清理；作者探索用 DWARF 调试信息等补救。**栈损坏与栈溢出**方面，展开器把自身上下文独立于被展开的栈保存，借助细胞元数据做健全性检查，并可用 TSS 的双重故障栈等"应急栈"继续处理。**依赖安全语言的局限**：所有组件必须用安全 Rust 编写；必须信任 Rust 编译器与 `core`/`alloc`（但不需要信任标准库，Theseus 未使用它），且构建系统以编译错误的形式实施类似能力（capability）的访问限制，加载器/链接器可作为第二层运行时校验。**状态溢出自由带来的全局知识减少**：系统没有全局内存分配清单，`MappedPages` 的拥有者被保证对映射拥有唯一控制权；内存紧张时的默认做法是杀死任务逐级回收，缓存类类型可主动向 OOM 处理器交出内存。**原型演化机制的局限**：只在引导时执行一次的初始化例程不会被新细胞"重放"，加载 crate 不会触发任何初始化函数。11.7 节指出语内设计有提升效率的潜力，11.8、11.9 节讨论把设计原则扩展到应用以及对 Rust 特性的期望（未逐页阅读后半部分）。

**第 12 章 结论（p. 123–124）**（未逐页阅读）
总结全文：状态溢出是许多计算目标的根本障碍，Theseus 通过细胞化的 OS 结构与语内设计把状态管理作为一等关注点，实现了轻松的在线演化、故障恢复与系统灵活性。

## 阅读建议

对中文读者，建议按以下顺序阅读原书：

1. **只读一章的话读第 1 章**：它完整交代了研究假设、两条主线（状态溢出研究 + Theseus 设计）与三条设计原则，是全书的地图。
2. **理解问题**（第 2、3 章）：先读第 2 章的状态溢出定义与粒度讨论（2.1、2.2 节，概念较抽象但值得细读），再读第 3 章的分类与实例（3.1 节的 Linux/VFS/MINIX/X Window 案例非常具体，可跳读）。
3. **理解方案**（第 4–6 章）：第 4 章读概览与 Rust 背景（熟悉 Rust 的读者可跳过 4.1）；第 5 章是全书结构设计的核心，必读；第 6 章重点读 6.1–6.2（语内设计的定义与两个手段）与 6.3.1（`MappedPages` 示例，配合代码清单阅读）。
4. **看收益**（第 8、9 章）：第 8 章读 8.1 的细胞交换四阶段与 8.2 的多级故障恢复；第 9 章以图表为主，重点看表 9.1（69% 故障恢复率）与图 9.1（演化各阶段耗时）。
5. **批判性阅读**（第 11 章）：了解 unsafe、异步展开表缺失、信任编译器等局限，避免把 Theseus 的结论过度推广。
6. 第 7 章可作为第 6 章的延伸（状态管理的具体手法）；第 10 章用作文献检索线索；第 12 章读结论收尾。

此外，建议与这些材料对照阅读：OSDI '20 的 Theseus 会议论文（约 18 页，适合快速把握全貌）、本目录下的 OSDI '22 海报译文（语内设备驱动，是语内设计在驱动方向的延续）以及 Ijaz 的硕士论文导读（把语内设计扩展到堆、ITC、网络与电源管理四个子系统）。
