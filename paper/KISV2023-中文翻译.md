## 摘要

本文报告了我们为一个基于 Rust 的开源操作系统 Theseus 提供轻量级正确性保证的经验。首先，我们报告了语内设计（intralingual design）方面的新进展：借助 Rust 的类型系统在编译期强制执行不变量，并信任 Rust 编译器。其次，我们提出了一种混合证明方法，它把形式化验证、类型检查与非形式化推理结合在一起。通过适当降低正确性保证的强度，这种混合方法*显著*降低了证明负担（proof burden）。我们分享了把该方法应用于 Theseus 内存子系统的经验，展示了其实用性，并量化了它所减少的证明工作量。

## 1 引言

正确性是操作系统（OS）这类复杂系统软件所渴望、却又难以获得的属性。实现正确性的一项关键技术是形式化验证（formal verification）。近年来涌现出多种形式化验证方法，它们在表达能力与证明负担之间做出不同的权衡，也就是"能证明什么"与"生成这些证明有多难"之间的取舍。然而，即便是所谓的*一键式（push-button）*方法 [25, 26, 28, 29, 33]，仍然背负着沉重的证明负担——即使面对非常小的软件系统、即使只证明非常有限的不变量，而这些不变量主要局限于一阶逻辑中可判定的部分。

本文介绍了我们近期在探索确保操作系统正确性新途径方面的经验。为了以较低的证明负担获得较高的表达能力，我们放宽了*正确性保证的强度*。我们观察到：虽然完整的形式化验证是理想的，但实现语言的类型系统（即 Rust）结合非形式化推理，同样可以提供较弱却明显有用的保证。

在 §3 中，我们进一步发展了 Theseus OS [8] 提出的语内设计思想，并用新的技术扩展其适用范围。语内设计利用语言级特性，借助编译器来强制执行不变量。我们分析了它的局限，指出 [8] 中所展示的不变量建立在一个不完整的基础之上：Rust 的所有权模型虽然保证某个线性类型的实例只有一个所有者，却无法保证同一线性类型的两个独立实例的实际值之间不存在意外的重叠。当线性类型实例表示一个系统资源时，这种重叠会让使用者用不同的实例并发访问同一资源。这一缺陷曾在 Theseus 的内存子系统中引发一个隐蔽的缺陷，我们报告了该缺陷并提交了解决方案。

因此，我们倡导一种混合方法（§4），它把语内设计、形式化验证与非形式化推理结合起来，为操作系统实现*轻量级*正确性。我们之所以称之为轻量级，不仅是因为与传统形式化验证相比它所需的工作量少得多，还因为它使用了非形式化推理并信任实现语言，因而保证的强度较弱。

在 §5 中，我们报告了把这一方法应用于 Theseus 内存子系统的修订版时的经验；这次修订为原有不变量提供了更强的保证，并消除了若干类隐蔽的缺陷。我们还分享了在 Rust 程序上使用方兴未艾的形式化验证工具（特别是 Prusti [6]）的经验。§6 中的结果表明，混合方法的开发负担很低，性能开销可以忽略不计。

综上，本文做出了三项贡献：

- 我们提出了一组新技术，用以扩展语内设计的适用范围与作用边界。
- 我们描述了一种混合证明方法，它把类型检查（语内设计所采用的方式）、形式化推理与非形式化推理结合起来，以提升操作系统的正确性。
- 我们报告了把这种低投入方法应用于 Theseus 内存子系统的经验。

## 2 背景与相关工作

Singularity [14] 使线性类型（linear type）在操作系统设计中广为流行，并将其用于跨软件隔离域的堆内存零拷贝共享。近期的一些工作利用 Rust 的线性类型系统来实现轻量级故障隔离 [24]、零拷贝通信 [27]、由编译器检查的会话类型 [15] 以及去中心化的资源管理 [8] 等特性。[7] 的作者还讨论了用 Rust 进行静态信息流控制与自动程序状态操作的潜力。Linear Dafny [19] 把线性类型用作 SMT 求解的补充手段，从验证条件中移除了内存推理。与之不同，我们的工作在设计并实现操作系统时，让 Rust 类型系统在与形式化验证的协作中提供超出安全性（safety）的保证。

（译注：严格来说，Rust 采用的是仿射类型系统（affine type system），它放宽了真正线性类型系统的限制，还允许"弱化"。〔原文脚注〕）

在构建 Verve OS [32] 时，Yang 和 Hawblitzel 创造性地把形式化验证与安全的实现语言结合起来：他们把操作系统划分为较低层的核心 *Nucleus* 和较高的内核，对用汇编实现的 Nucleus 进行安全性与正确性形式化验证，而内核的安全性则依赖实现语言（C#）。我们的混合方法并不追求把操作系统清晰地划分为已验证与未验证两部分；相反，在任何一个想要证明其不变量的子系统中，我们都组合使用多种证明技术，让正确性性质与最适合它的证明技术相配对。

许多工作利用 Rust 的类型系统来确保超出安全性问题之外的正确性。在 §3 中进一步发展这些思想之前，我们先对它们做一概述。

***用线性类型处理成对操作：***许多操作必须成对出现，例如内存的分配/释放、锁的获取/释放、引用计数的递增/递减。人工跟踪成对操作十分困难，因为第二个操作可能比第一个晚很多才发生，而且发生在代码的不同位置。这类成对操作的失配在 Linux 内核中很常见 [20, 21, 31]。使用线性类型可以解决这一问题：把第一个成对操作放进构造函数，把第二个放进析构函数。Rust 自身在为堆分配的数据结构（`Vec<T>` [4]）、锁（`MutexGuard<T>` [3]）和引用计数指针（`Arc<T>` [2]）提供类型时，就遵循了这一设计模式。

***作为不可伪造且唯一能力的线性类型：***在 Rust 中，只要某个线性类型的实例没有实现 `Clone` trait，它就是一个*唯一的*且*不可伪造的*能力（capability），也就是说无法被复制 [17, 24]。这种实例的所有权会自动授予使用它的权利，无需在运行时检查其真实性 [10, 24]。由于该能力具有线性类型，因而只有一个所有者；我们可以利用 Rust 内建的所有权规则来防止数据竞争，并自动插入资源清理代码。在 §3.1 中，我们从这一思想获得启发，把线性类型实例用作操作系统资源的表示。

***用线性类型实现静态强制的状态机：***通过使用行为类型技术（例如类型状态 typestate 与会话类型）来实现状态机，线性类型系统能够在编译期阻止错误的状态机转换。与线性类型结合后，类型状态协议可以得到静态验证 [10]，不带来任何运行时开销。

## 3 语内设计

语内设计 [8] 的目标是最大化编译器在强制执行正确性方面的作用：利用编程语言特性（即类型系统）把*系统需求*更精确地传达给编译器。换言之，它*把需求编码进实现本身*，从而使编译器能够强制执行这些需求（译注：原文此处写作 "cannot be enforced"，按上下文应为笔误）。由于类型系统的表达能力不足以传达许多需求，这些需求无法被如此编码；我们把这类需求归为*语言外（extralingual）*需求。本文的目标是在近期工作（§2）奠定的基础上，提出一套把线性类型以及其他基于类型的技术纳入底层系统设计的*系统化方法*。

### 3.1 语内表示系统

我们提出语内表示系统（Intralingual Representation System, IRS），把管理系统资源的部分责任从运行时的操作系统转移到编译器。通常，操作系统会创建软件对象来表示物理或抽象资源，例如 Linux 中表示物理帧的 `struct page` 对象。IRS 借助线性类型把资源的*表示*与使用它的*权限*结合在一起：线性类型实例的所有权即代表使用该资源的唯一权限。我们把这种实例称为资源的一个表示。IRS 中的表示由编译器检查，这意味着（i）任一时刻对某个表示至多存在一个可变引用，（ii）对该表示的访问受到类型系统所传达规则的约束。Rust 这类强类型语言已经把线性类型实例用作内存对象表示的有限形式，而 IRS 把这一点加以扩展，使表示类型能够应用于内存之外的任意系统资源。

***通过类型状态改变访问权限。***在 IRS 中，一个表示的访问权限由其类型的公开可见方法定义。每一组彼此不同的访问权限由一个类型状态（typestate）表示，表示的访问权限会随状态转换而改变。状态转换方法接收一个表示作为输入，*消耗（consume）*它并改变其状态。例如在清单 1 中，*Pages* 实例是一种可处于四种状态之一的表示：Free、Allocated、Mapped 或 Unmapped [16]；它的方法在这些状态之间转换表示，例如 L16 处的 `unmap()`。编译器可以强制对表示的访问遵守其当前状态施加的限制。例如，在 Free、Allocated 和 Unmapped 状态下，尚未为给定的 Pages 建立页表项（page table entry, PTE），因此该 Pages 表示不能用于访问底层内存范围。这一点通过*只为*处于 Mapped 类型状态的 Pages 实现 `read()` 和 `write()` 方法（L14）而得到静态保证。

***通过所有权转移、共享与借用进行委托。***在 IRS 中，表示是一个单例（singleton）实例：要么只有一个独占所有者，要么有多个只能通过互斥机制可变地访问它的所有者。这两种情形都遵循"同一时刻对一个类型至多存在一个可变引用"这一 Rust 不变量。所有者可以通过以下三种方式之一授予对表示的访问权，从而方便地委托权限：（i）把所有权转移给获得完全独占访问权的新所有者；（ii）通过引用计数的智能指针共享所有权，使多方共同拥有该表示；或者（iii）临时地（在作用域内）借给一个能通过引用访问该表示的借用者。

***通过自动析构函数返还表示。***我们可以把"插入顺序正确的清理序列"这一复杂责任转移给编译器：把全部清理代码放进线性类型的析构函数（即 Rust 的 `Drop` 处理器）中。这一点对于那些表示永不应被销毁的物理资源（例如物理帧）的表示尤为重要；这类表示必须返还给操作系统以备后用。在使用类型状态时，一个表示可以拥有多个 drop 处理器，每个状态一个；每个状态的 drop 处理器会撤销进入该状态时所做的改动，把表示恢复到先前的状态。初始状态的 drop 处理器最终把实例交还给操作系统保存。例如在清单 1 中，处于 Mapped 状态的 Pages 的 drop 处理器会移除各 PTE 并把它转换为 Unmapped 状态（L28）。随后，各个前驱状态的 drop 处理器被迭代调用，直到 Pages 实例回到 Free 状态，此时 `Pages<Free>` 实例被交还给由页分配器维护的空闲页块红黑树（L22）。

```rust
1   // Pages is a representation of a range of virtual pages.
2   struct Pages<S: State> {
3       range: RangeInclusive<usize>,
4   }
5   // The possible states a Pages instance can be in.
6   enum State {
7       Free,
8       Allocated,
9       Mapped,
10      Unmapped
11  }
12  // Only Pages in the Mapped state have memory access functions.
13  impl Pages<Mapped> {
14      pub fn write(&mut self, data: [u8]);
15      pub fn read(&self) -> &[u8];
16      fn unmap(self) -> Pages<Unmapped>;
17  }
18
19  impl<S: State> Drop for Pages<S> {
20      fn drop(&mut self) {
21          match S {
22              State::Free => {
23                  // Re-take ownership of the pages by replacing it
24                  // with an empty range; return it to page allocator.
25                  let pages = replace(&mut self.range, Pages::empty());
26                  free_pages_list.insert(pages);
27              },
28              State::Mapped => {
29                  // PTEs have been cleared, so we transition
30                  // the Pages to the Unmapped state.
31                  let pages = replace(&mut self.range, Pages::empty());
32                  pages.unmap(); // Drop the returned Pages<Unmapped>
33                  ...
34              }
35          }
```

***表示 vs. 能力。***表示这一概念可能让读者联想到能力（capability）。与能力一样，表示也是*不可伪造*且*可委托*的。与能力不同的是，表示是*唯一的*：系统中不会存在两个对应同一资源的表示。这就排除了*派生（derivation）*，即在系统中同时存在多个具有不同访问权限的能力副本。重要的是，正如 [23, 30] 所报告的，仅靠语言级机制不足以实现能力系统的全部特性。Redleaf [24] 使用线性类型实例在隔离域之间实现细粒度的访问控制，但并未尝试构建一个完整的能力系统。

### 3.2 作为工作证明的线性类型

我们使用线性类型的另一种主要方式，是通过让某个函数返回一个专用类型实例来表明该函数已被执行。在这种用法下，线性类型实例不再表示一种*空间性*资源（如类型状态中那样），而是作为某个*时间性*动作已经发生的证明。用于此目的的线性类型就是一个只能由执行所需*工作*的单一函数来实例化的类型。为防止该类型的实例在其他任何地方被创建，我们确保它由一个*私有的*内部类型组成，而该内部类型在类型所属模块之外不可访问。

把*作为工作证明（proof of work）的线性类型*与强类型的函数接口结合起来，可以在操作的不同"阶段"之间静态地强制顺序。也就是说，我们可以构造一条函数链：一个函数创建并返回一个线性类型实例，供下一个函数消耗，这实际上要求线性类型的每个实例都按照它被创建的顺序被使用，工作才能向前推进。事实上，这种"先实例化、后消耗"的模式是我们使用线性类型的诸多方式（§2）的核心，此处不同之处仅在于类型实例所代表的东西。

例如，Theseus 的页表项（PTE）`unmap` 函数会返回一个 `UnmapResultT` 实例，其中保存了刚被解除映射的物理帧的信息。`into_unmapped_frames()` 通过消耗该 `UnmapResultT` 实例——作为这些帧现已空闲的证明——为这些帧重建一个表示。它可以在 PTE 被清除很久之后才被调用，而帧表示在那之前不会被重建，从而保证其唯一性。这里的 `UnmapResultT` 并不是指向新近解除映射的物理帧的表示：它不存在多种状态，也不提供对任何资源（在此例中为内存）的访问。它只是一个代表"PTE 已被清除"的一次性类型实例，因此类型状态模式在此并不适用。

### 3.3 语内硬件抽象层

语内硬件抽象层（Hardware Abstraction Layer, HAL）在与硬件设备通信时强制执行由数据集给出的规则，而不需要任何运行时检查。我们用一个 `struct` 来表示内存映射 I/O（MMIO）寄存器和其他 I/O 数据结构的布局，然后可以把它覆盖到某段内存区域之上。这保证了每个寄存器和位域总是在底层内存区域中以其正确的偏移（和对齐）被类型安全地访问。我们的做法排除了访问 MMIO 寄存器时常用的 unsafe 指针运算，而编译器无法对这种运算进行推理。

借助类型系统技术，我们还能进一步防止对 MMIO 的错误读写，具体如下：

1. `struct` 字段上的类型包装可以强制 volatile 访问以及只读或只写限制。
2. 标记为保留（reserved）的字段在 `struct` 中具有私有可见性，因而在 HAL 之外不可访问。
3. 只有每一位都无任何限制、均可访问的字段才是公开可见的。
4. 对可写入取值有限制的字段只能通过 `struct` 方法访问。一个 `enum` 编码了合法取值的集合，必须作为方法参数传入，从而在编译期禁止任意的原始值。
5. 把线性类型用作工作证明，我们可以在对不同寄存器的相继读写之间、甚至在同一寄存器中互不重叠的位域之间静态地强制操作顺序。

### 3.4 语内设计的局限

语内设计虽然强大，但也有许多源自其对语言类型系统依赖的不足。首先，由于类型系统能强制执行的不变量有限，它不如许多形式化验证技术那样具有表达能力。一般而言，它无法证明任何算法性质，例如某个 `sort()` 函数确实完成了排序。

此外，它也无法对不受限类型的来源或其中存放的值进行推理。这一限制在操作系统中是根本性的：为了与硬件交互，最底层必须使用内建的非受限数据类型，即原始类型或基本类型，例如 Rust 中的无符号整数 `u32`。仅凭类型系统无法对在最底层原始基本类型上读出或写入的值的正确性提供任何保证。

最后，IRS 设计用一个线性类型实例来表示一个操作系统资源，*而线性类型系统本身无法保证所表示资源的唯一性。*这超出了基于 Rust 所有权模型的语内（类型级）唯一性：同一线性类型的两个变量不能拥有同一个值（内存对象），但无法保证这些值（内存对象）所表示的资源互不重叠。一旦发生重叠，该类型的多个实例就能访问同一资源，也就是彼此重叠的部分。这一限制正是我们在 Theseus 内存子系统中发现一个重要缺陷的根源，将在 §5.4 中讨论。

## 4 面向正确性的混合方法

为了克服语内设计的局限与形式化验证沉重的证明负担，我们主张采用一种混合方法：让正确性性质与证明技术相配对。在选择证明技术时，我们会权衡证明投入、保证强度与性能。我们的混合方法结合了形式化验证、类型检查（语内设计所采用的方式）、人工代码审查以及散文式证明（prose proof）。我们只对选定的性质使用基于 SMT 的 Rust 形式化验证工具 Prusti [6]，而对更高层的不变量则借助非形式化推理，尤其是散文式证明。散文式证明可以把由不同证明技术证明的不变量（以及以不同语言指定的不变量）"缝合"在一起，而不需要统一的形式化规约；避开这一要求显著降低了证明负担。在散文式证明中，我们用自然语言表述由各种技术证明的不变量，并论证这些不变量如何组合起来蕴含一个高层次的不变量。

鉴于线性类型系统本身无法保证实例所表示资源的唯一性，而这种唯一性又正是 IRS（§3.1）的基础，线性类型实例的唯一性就是形式化验证的绝佳对象。要形式化验证某个线性类型实例是唯一的，我们只需形式化验证该类型的构造函数绝不会创建表示重叠资源的实例。

### 4.1 最小化证明负担

由于形式化验证是我们混合方法中证明负担的主要来源，我们借助类型系统以如下方式强化形式化验证的成果：（i）若复合类型的成员是唯一的，则其实例也是唯一的。因此，没有必要对 IRS 中每个表示的实例唯一性都做形式化验证；只需验证系统中若干选定基本类型的实例唯一性（例如清单 1 中的 `Pages`），就可以依靠类型系统确保由这些基本类型构成的类型的实例唯一性。例如，设备 MMIO 寄存器的表示由一个 `Pages<Mapped>` 实例构成，因而借助这一性质无需形式化验证即可证明其唯一。（ii）通过形式化验证泛型代码，被验证的性质对其所有具体实例同样成立。除了泛型数据结构之外，在验证那些表示相似资源的类型的方法时，我们同样可以使用泛型。

### 4.2 语内规约

语内设计与散文式证明都可能做出基于类型的假设。我们利用 Rust 的语言机制来指明这些假设，使它们能在编译期被检查。据我们的经验，常见的基于类型的假设包括但不限于：（i）某类型不实现某些 trait；（ii）某类型由另一类型构成；（iii）某函数消耗某类型的一个实例；（iv）某类型的内部字段是私有的。例如，清单 1 中 `Pages` 类型的实例需要是唯一的。这一唯一性的证明要求该类型是线性的，且不暴露其内部字段。这两个要求可以分别通过不为 `Pages` 实现 `Clone` 与 `DerefMut` trait、以及把它的 `range` 字段设为私有来编码。代码库中的一个改动（例如某位粗心的开发者为 `Pages` 实现了 `Clone`）可能会在无意间破坏唯一性证明。由于这些改动并不违反 Rust 的类型规则，编译器无法捕捉它们。

为了在编译期检查这类基于类型的假设，我们使用静态断言（static assertion），并可以把它们组织在与代码库分开的单独文件中。这些断言会生成代码，一旦断言不满足就中止编译。例如，为阻止为 `Pages` 类型实现某些 trait，我们可以在清单 1 中加入这一行：

```rust
assert_not_impl_any!(Pages: DerefMut, Clone);
```

这些静态断言构成了关于类型假设的语内规约（intralingual specification）。

### 4.3 性能与验证投入的权衡

由于类型检查发生在编译期，大多数语内设计思想不会带来任何运行时开销。然而，如果我们把语内设计推向极致，使尽可能多的代码在编写时就让编译器能够推理其正确性，那么 IRS 设计就可能造成运行时开销。在这样的设计中，所有物理资源都以其最细粒度用从不被销毁（drop）的线性类型实例来表示，操作系统把这些实例（表示）存放在一个数据结构中。这种设计并不总是可行：一来存储和查找表示需要额外的时间，二来当表示所代表的资源不复存在时（例如内存热插拔），可能需要销毁该表示。对于前一种情况，如果我们能够接受在表示被 drop 之后重建它所需的额外证明投入，就可以避免这部分开销。对于后一种情况，我们还需额外验证表示的 drop 处理器会更新系统的簿记状态，从而在设备重新插入时能够重建其表示。

例如，一个完全语内的页表设计会使用线性的 `PTEs` 类型，其实例既拥有承载一组页表项（PTE）的内存，也拥有表示这些 PTE 所映射帧的 `Frames` 实例。`map`/`unmap` 函数会用编译器能够理解的类型安全代码在数据结构中查找 `PTEs` 实例。这种设计由于要把所有表示存储为细粒度的软件对象而增加内存使用，并因查找 PTEs 而产生额外的周期开销。

我们最终为 Theseus 选定的设计以额外的验证投入为代价来避免这些开销。我们把页表表示为单个线性类型实例，而不是 PTE 的集合；查找 PTE 的语言外表遍历属于 HAL 的一部分。映射过程会"遗忘" `Frames<Mapped>` 实例，以避免解除映射时查找它们的开销。作为替代，解除映射并清除 PTE 的函数会返回一个 `UnmapResultT`，它作为帧已被解除映射的*工作证明*；随后，一个经过验证的函数会从该 `UnmapResultT` 重建 `Frames` 实例。

## 5 案例研究：Theseus 的内存管理

接下来我们报告把语内设计与混合方法应用于 Theseus 内存子系统的经验。

### 5.1 内存子系统的语内设计

我们依照语内设计模式（§3）重新设计了 Theseus 内存子系统的若干部分。遍历页表和更新 PTE 的函数被归入内存子系统的语内 HAL：PTE 总是通过类型安全的接口来操纵。我们用 IRS 创建了 `Frames` 和 `Pages` 两个类型，其实例分别是某段物理内存或虚拟内存的唯一表示。借助类型状态编程，我们为 `Frames` 和 `Pages` 类型的实例设立了四种可能的状态：Free、Allocated、Mapped 和 Unmapped。`Pages<Mapped>` 实例（表示可访问的内存）按照 Rust 类型系统的规则使用：要么一个可变引用，要么多个不可变引用，对应于对底层内存的单写者或多读者，但二者不能同时存在。`Pages` 类型的详细代码示例见清单 1。

### 5.2 双射映射不变量

Theseus 的双射映射不变量（bijective mapping invariant）陈述如下：

**不变量 1（双射映射）。** *系统虚拟地址空间中的每一页只能映射到物理地址空间中的一个帧，反之亦然。*

该不变量可以等价地表述为"一个帧只能出现在单个 PTE 中"。它可以防止语言外的别名共享，而这种共享的消除对于为*全部*系统内存提供内存隔离与安全性是必需的，而不只是针对 Rust 内建的安全堆与栈内存支持。*Theseus 在不使用硬件地址空间的情况下实现隔离，依赖于该不变量始终被维持。*

Theseus 的内存子系统只在创建 `Pages<Mapped>` 实例时添加一个 PTE，并且只在 drop 同一实例时移除它。因此，要证明双射映射不变量，就必须证明 `Pages<Mapped>` 实例的正确构造与正确析构。

### 5.3 证明概要

我们使用正确性混合方法（§4）给出双射映射不变量的散文式证明，其中明确说明每种证明技术被用在何处。我们列出证明该不变量所需的各个引理，并在每个引理旁列出证明它所用的技术：形式化验证（F）、类型系统（T）或人工检查（M）；再用散文式证明（P）把多种技术联系在一起。我们的证明 [1] 基于以下四个引理。

**引理 1.** `Frames` 与 `Pages` 实例是唯一的。[F, T, M, P]

**引理 2.** 一个 `Pages<Mapped>` 实例只能通过同时取得 *`Pages<Allocated>`* 实例和 `Frames<Allocated>` 实例的所有权来创建。[T]

**引理 3.** PTE 只能通过内存子系统的 `map` 和 `unmap` 函数来操纵。[T, M, P]

**引理 4.** 创建 `Pages<Mapped>` 实例时*只为*给定的页与帧添加 PTE；drop 它则会移除这些 PTE。[M]

引理 1 保证了在创建 `Pages<Mapped>` 时，即将被映射的页与帧的表示是唯一的。引理 2 保证在该映射存在期间，这些页/帧不能被用于任何其他映射。引理 3 保证映射无法以绕过 `Pages<Mapped>` 所提供保证的方式创建。引理 4 保证软件状态准确反映硬件状态，从而使编译器能够强制执行关于页表内容的不变量。我们的证明不涉及 TLB 击落（shootdown），尽管 `unmap()` 确实会发送它们，以防止硬件缓存那些软件中已不存在的无效映射（引理 4）。

### 5.4 引理 1 的证明：揭示出的缺陷

引理 1 的证明大大增强了双射映射保证的强度。为了证明该引理，我们引入了线性类型 `Chunk`——一个围绕 `RangeInclusive<usize>` 的不可 `Clone` 的包装类型——并形式化验证所有创建或修改 `Chunk` 的方法，以确保来自同一分配器的任意两个 `Chunk` 实例的区间不会重叠。我们将其内部字段设为私有，以防止在其方法之外进行可变访问，并人工检查 `Chunk` 实例只在其经过验证的方法中被可变地访问。`Chunk` 的这些联合性质证明了每个实例都是唯一的。`Frames` 与 `Pages` 都仅由 `Chunk` 类型构成；一条静态断言检查这一组合关系始终成立。于是，`Frames` 与 `Pages` 通过组合获得唯一性，而这一保证由 Rust 语言提供——这正是类型系统把经过形式化验证的不变量扩展到其他类型的一个例子（§4.1）。

最初的 Theseus 用人工检查代替形式化验证来证明引理 1，因为唯一性超出了语内设计的范围。在帧分配/簿记代码中，我们发现了一个缺陷，它导致创建了相互重叠的 `Frames` 实例，违反了双射映射不变量。该缺陷只在一个非常特殊的代码路径中显现，而这条路径在帧分配器代码投入使用的四年里从未被触发。它使网络驱动程序的开发停滞了一个多月，这促使我们探索把形式化验证纳入语内系统的方法。

### 5.5 应对 Prusti 的局限

我们选择 Prusti [6] 作为验证工具。与 Verus [18] 等其他工具相比，Prusti 在开发和文档方面更为成熟 [5]。

在最初编写帧分配器和页分配器中经过验证的部分时，我们必须克服 Prusti 的某些限制，以便更好地平衡验证投入与系统性能（见 §4.3）。其中一个限制是 Prusti 的函数规约不支持对用户自定义类型做比较运算。这带来了问题，因为 Rust 的一个主要优势在于其零成本抽象，而这通常通过 newtype 包装模式实现。我们选择为 newtype 自行实现比较运算符，而不是维护两套相同的数据（一套是可在已验证代码中使用的原始类型，另一套是 Theseus 其余部分使用的 newtype）。这增加了我们的代码量，但我们能够在更高的抽象层次上验证代码，并避免了维护同一数据两份副本的开销。Prusti 的另一个限制是对 Rust 泛型的支持不完整。我们最初尝试实现可同时用于页分配器和帧分配器的泛型数据结构时，导致了 Prusti panic。我们不得不在分配器内部复制代码，从而增加了代码量与验证时间。

在用我们的变通办法完成第一版实现之后，我们把发现报告给了 Prusti 的开发者，他们随后及时修复了这些问题。这印证了我们的判断：这些限制并非我们的方法或基于 Rust 的验证工具的根本缺陷，而是使用一个仍在积极开发中的工具所致。在应用了他们提供的修复之后，我们得以在代码中轻松使用 newtype 和泛型数据结构，从而实现经过验证的代码复用并减少验证投入。作为未来的工作，我们将进一步整合经过验证的代码，构建一个可同时被 `Pages` 与 `Frames` 分配代码使用的通用 chunk 分配器。

## 6 评估

我们评估了 Theseus 新内存子系统的性能并量化了验证投入。我们的目标是找出由验证过程引起的代码改动所导致的任何性能差异。此外，我们评估了形式化验证帧/页分配器各部分所需的证明投入，以衡量混合方法的"轻量"程度。

### 6.1 性能对比

我们发现包含形式化验证代码的 Theseus（Verified Theseus）与没有任何验证代码的原始 Theseus 性能相当。我们在一颗主频 2.30 GHz、关闭超线程的 Intel(R) Xeon(R) Gold 6252N CPU 上运行了两个内存子系统微基准测试。第一个微基准是 Rust 版本的 LMbench [22] 内存映射测试：在该基准中，一个 4 KiB 页被映射、写入并解除映射 100,000 次。两个版本的 Theseus 表现出完全相同的性能，平均时间为 199 μs，标准差小于计时器周期（42 ns）。第二个微基准取自最初的 Theseus 论文 [8]，它分别测量映射一个页、重映射以及随后解除映射所需的时间，并不断增加映射数量。图 1 显示两个版本之间没有显著差异。

### 6.2 验证投入

表 1 报告了 §5 所述 Theseus 内存子系统的规模（以 SLOC 计）与验证时间。我们发现，其证明投入比端到端形式化验证系统低几个数量级，而验证时间在几分钟之内。所有验证时间均使用 2023-08-22 版的 Prusti 测量，运行环境为 Ubuntu 20.04、主频 2.5 GHz 的 Intel Core i7-1260P CPU。

内存子系统中经过形式化验证的部分由四部分组成：（i）为 Rust 核心库中的类型编写的 Prusti 外部规约；（ii）泛型数据结构；（iii）帧分配器代码中包含创建和修改 `Chunk` 的方法的部分；（iv）页分配器代码中与帧分配器几乎相同的部分。如 §5.5 所讨论的，我们可以通过用泛型整合页分配器与帧分配器来进一步减少代码量。

**证明投入：**我们的"证明代码与实现代码之比"为 1:76。这比用 Rust 编写的端到端验证页表实现 [9] 的 10:1 低两个数量级。其他完全验证的工作报告的证明与实现之比在 5:1 到 20:1 之间 [11–13, 16]。

如此之少的证明投入是我们混合方法的直接结果，其代价是保证强度较低以及更大的可信计算基（TCB）。我们只对唯一性这一条性质使用 SMT 验证，并用其他技术来推理对页表写入的正确性。

**可维护性：**只有当 chunk 分配器模块内部发生变化时，我们才需要重新验证代码。根据我们的经验，由于验证时间很短（约两分钟），对 chunk 分配器的设计进行试验十分容易。最重要的是，改动 chunk 分配器模块之外的任何代码都*不需要*重新验证。
