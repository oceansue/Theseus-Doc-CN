## 摘要

在以往的工作中，我们已经指出：未被充分诊断的状态溢出（state spill）问题，是实现易于维护、易于演化且能可靠运行的复杂系统的一道障碍。本文分享我们从零开始构建 Theseus 的早期经验——这是一个以消除状态溢出为指导原则的操作系统。Theseus 从分布式系统中汲取灵感来重新思考状态管理，并利用 Rust 语言特性以获得最大的安全性、代码复用与高效的隔离。我们打算把 Theseus 展示为一个*运行时可组合（runtime composable）*的操作系统：其中的实体可以方便地互换，并且能够在不重新配置或重启的情况下独立演化。

## 1 引言

如今的单机操作系统规模庞大且异常复杂，是由组件纠缠而成的网络，几乎不可能解耦，这使得系统难以维护、难以演化、难以安全地更新，也难以可靠运行。摩尔定律的终结加剧了这一问题：计算机硬件的升级周期被拉长 [2]，大多数演进性的进步只能发生在软件之中。一个突出的例子是 DARPA 推动软件系统"在超过 100 年的时间里保持健壮且可用" [1]，这远远超出了其最初设计者与硬件的寿命。

因此，对一个*去纠缠（disentangled）*的操作系统的需求日益迫切：它应当允许每个组件独立演化，最好能在运行时进行，而不必担心某个组件的故障会危及其他组件。

现有系统的设计原则与实践促成了沿多个维度的解耦策略探索，但它们都未能达到去纠缠以及上述目标。首先，传统的*模块化（modularization）*遵循关注点分离原则，把庞大的单体系统分解为更小的、理想情况下相互正交的、包含相关功能的实体。系统中的基本模块化能够实现*某些*软件工程目标，例如代码复用，却常常因为造成紧密耦合而阻碍其他目标——为 Linux 引入在线更新 [5, 8, 30, 41] 与故障隔离 [23, 43, 44] 所需的巨大努力便是明证。其次，基于*封装（encapsulation）*的解耦策略（例如面向对象编程 OOP）遵循最小知识原则，把相关的代码和数据归组到单个实体之中，并在实体之间设置严格的接口边界。它们获得了更好的可维护性与适应性，却仍然落入与上述相同的问题 [15, 16, 42]。第三，*特权级分离（privilege level separation）*见于微内核操作系统，它通过强制实体在相互隔离的域中运行、并以特权级作为边界来解耦实体。微内核把内核功能推入用户态服务器进程，以便在较粗的空间粒度上解决故障隔离 [21]，但由于服务器之间需要密切协作，演化依然困难 [20]。

最后，由*硬件*驱动的解耦策略借助经典的分布式系统原则，并根据底层硬件结构（例如核心、一致性域等）来选择实体边界。单节点机器如今已经接纳了松耦合的异构处理单元，这启发了近期的操作系统工作，如 Barrelfish [10]、Helios [33]、fos [45] 和 K2 [29]：它们重构内核，通过在各个核心上（大体）独立运行的软件实体副本，实现高度可扩展的性能。虽然这些方法提升了可扩展性，但它们并未解决演化、运行时灵活性或故障隔离的问题。

### 我们的方法：免于状态溢出

我们认为，操作系统实体之间的状态溢出是操作系统中相互纠缠的根本原因，而以往的解耦策略都忽视了这一点。状态溢出描述的是这样一种现象：一个软件实体的状态因为处理与另一个实体的交互而发生*持久性的改变* [12]。状态溢出简洁地指出了许多理想的操作系统目标之所以难以实现的底层原因，包括故障隔离与容错、在线更新与热替换、可维护性、可扩展性、进程迁移等等。我们相信，与"耦合"这类既有术语相比，状态溢出能更好地刻画这些操作系统挑战；优先处理状态溢出，比优先考虑上述解耦标准更能带来去纠缠的设计。

在本工作中，我们提出 Theseus¹——一个用 Rust 从零开始编写的新操作系统，它具有独特的扁平软件架构，以及一种*仅由状态溢出的表现形式来引导*的解耦策略。在设计中的每一步，我们都把消除状态溢出或减轻其影响置于其他任何标准之上，例如性能、编程的便利性等等。Theseus 的设计完全独立于底层硬件，并把分布式系统与 RESTful 架构的原则融入单节点操作系统。因此，Theseus 遵循严格的设计原则，例如无状态通信、摒弃传统的封装等等。

（译注：忒修斯之船（The Ship of Theseus）是一个悖论式的思想实验：如果一艘木船的每一块木板都随时间被逐渐替换，它还是原来那艘船吗？〔原文脚注〕）

促使我们设计 Theseus 的主要目标是*在最大程度上消除状态溢出*，从而为整个操作系统中的所有组件——包括核心内核实体——带来*运行时可组合性*。Theseus 的运行时可组合性允许任意实体在运行时被单独替换，而无需重新构建或重启系统。这与现有操作系统中只允许在编译期重新配置的可组合模块或静态可组合性不同。我们预期这一性质将使一个正在运行的 Theseus 实例能够持续演化，以满足新的需求和用例。

我们目前正使用 Rust 实现 Theseus。Rust 是一种现代系统语言，它提供高层的零成本抽象与内存安全，同时保留对底层编程结构的访问能力。Rust 不需要运行时系统或垃圾回收，因此非常适合操作系统开发；它强调把运行时复杂性转移到编译期，这与 Theseus 的设计原则十分契合。我们表明，Rust 的许多语言级特性（例如基于仿射类型的所有权系统）使得实现经典操作系统目标（如隔离）以及新目标（如安全性与去纠缠）都变得容易得多。

在本文中，我们分享设计与实现 Theseus 早期阶段的经验，包括设计原则与主要的设计决策。

## 2 设计原则

由于 Theseus 的使命陈述是*把消除状态溢出置于一切之上*，我们在此简要解释这一概念。状态溢出记作 S -> D，是一种有害现象：软件实体 D 的状态因为处理来自另一个实体 S 的交互而发生持久性的改变 [12]。这里，S 表示发起与*目的实体* D（服务器/被调用者）之间交互的*源实体*（客户/调用者），D 负责处理并响应这一请求。状态溢出并非在每次交互中都会发生，而是只有当实体 D 内部状态的改变在其与 S 的交互*结束之后*仍然持续存在时才会发生。

在本节中，我们提出 Theseus 在设计上必须遵循的原则，以避免状态溢出，从而实现恰当的去纠缠与运行时可组合性。在某些情况下，这些设计原则代表一种理论上的理想状态，可能无法完全达成；这一点将在 §3 中讨论。

### 2.1 基于状态溢出解耦实体

Theseus 所采用的解耦策略优先消除实体之间的状态溢出，然后才考虑其他任何标准，例如编程的便利性、性能或与硬件结构的匹配。这带来了一套颇为非正统的模块化原则，它更接近 REST 架构 [18]，而非经典的分解建议 [36]（译注：原文此处作 "orthodox"，按上下文应为 "unorthodox"，即"非正统"）。

***无封装原则：***一个实体不应为另一个实体保管状态，也就是说，在 S -> D 的交互之后，D *不*应持有表示该交互进度的已更新状态。相反，实体 S 应当持有该状态，但必须无法理解或修改它。这一原则摒弃传统的封装，以便在两次交互之间恰当地解耦这两个实体，同时又保留了信息隐藏（就隐藏数据而言，而非隐藏实现细节 [36]）。

经典封装规定相关的代码与数据应当被一起包含在同一个实体之中，这通常被认为是良好实践，因为它不鼓励依赖全局状态或外部实体中的数据。在实践中，这意味着实体运行所需的全部状态都完整地包含在其内部；推而广之，一个实体会内部保存*其他实体与它交互时已取得的进度*。因此，Theseus 拒绝经典封装，因为它会直接导致状态溢出：当客户实体 S 调用服务器实体 D 中的一个函数时，D 就必须在内部保存由 S 的这次函数调用引起的进度变化，从而造成 S -> D 的状态溢出。

***无状态通信原则：***任何交互 S -> D 都必须包含目的实体 D 处理该交互所需的全部数据。由此可自然推出：D 只需要访问*从 S 传入的*数据，因此可以*被限制*为只访问这些数据而不能访问其他状态。无状态通信并不意味着交互不包含状态，而是说交互本身并不代表 D 在有限状态机表示中的进度。这样做的主要好处是不对先前状态做任何假设，这意味着一个实体可以是无状态的——它无需在交互之间保存中间状态，因为未来的交互将是自给自足的，因此状态溢出不可能发生。

### 2.2 组装一个去纠缠的操作系统

上述两条原则关注的是成对的解耦，接下来的两条原则则关注构成完整操作系统的大量实体之间的去纠缠。

***通用且无连接的接口原则：***所有实体及其功能都应当能够通过统一的调用接口方便地访问，并且不应对某个接口的持续可用性抱有期待。统一的可访问性将促进实体的可互换性，并使现有接口与新接口的平滑集成成为可能。这一原则受到 RESTful 架构 [18] 的启发，也让人联想到 Web 接口允许用户浏览可用内容并对链接做临时缓存的方式。

***模式复用原则：***常见的、重复出现的操作系统设计模式，例如多路复用器、间接层与分发器，应当只实现*一次*并在整个操作系统中复用，从而降低添加匹配这些模式的新特性时的开发风险。把一个已知安全的模式实例化为某个具体实体应当可以在编译期完成，并且无论怎样定制参数化，该模式都必须保证不产生状态溢出。此外，所有实体——尤其是模式——都应当具有*狭窄*的适用范围，也就是说，单个实体只应包含一项主要功能，而不是多个不可分割的特性。

## 3 Theseus 的设计与实现

现在我们把 Theseus 的设计与实现放在一起描述，因为实现的性质在很大程度上决定了我们的设计原则是否得到遵守。目前，我们的实现是一个用于对比与状态分析的基线操作系统，用 Rust 从零开始编写；我们正在按照下文的概念逐渐把它转变为无溢出的设计，其中大部分概念尚未实现，而且可能发生变化。*从现在起，我们交替使用"实体"与"模块"这两个词，原因将在下文说明。*

### 3.1 扁平模块架构

现有的单体内核与微内核操作系统都采用复杂的层次化模块架构：一个模块可能把状态溢出到另一个模块，或者一个模块可能把其他模块作为子模块包含进来，如图 1(a) 与 (b) 所示。状态溢出与模块层次相结合，导致模块之间相互纠缠。与之相反，Theseus 采用一种非传统的*完全扁平*的模块模型，禁止模块之间存在任何层次关系，如图 1(c) 所示。因此，一个模块既不能包含子模块，也不能作为另一个模块的子模块；我们强制要求把子模块剥离为独立的、一等公民的模块，并与其他模块保持无溢出的接口。这一不变量只涉及模块的结构与布局，与通信无关；任何模块都可以直接与任何其他模块的公共接口交互（§3.4）。

*【图 1：(a) 单体内核与 (b) 微内核操作系统的架构允许嵌套的模块层次，这显著增加了对每个模块/子模块进行管理的复杂性，尤其是在状态溢出造成纠缠的情况下。Theseus (c) 在内核实体之间强加扁平的层次结构，其中子模块必须被抽取为独立的一等模块实体，并具有无溢出的公共接口。禁止层次化的包含关系降低了模块的复杂性与管理逻辑，有利于去纠缠与可互换性。（图略，见原 PDF 第 3 页）】*

此外，Theseus 的扁平模型通过引入单一根模块 *nano*-core 来直接管理系统中的每一个模块，从而简化了模块管理。这个名副其实的 nano-core 范围极其精简：它只负责引导操作系统，并建立最基本的虚拟内存，使模块能够被加载和替换，包括它自身。层次化模型虽然看似更简单，但实际上会把管理逻辑与状态转移到每个父模块中，从而造成额外的状态溢出。这会要求以不同方式对待父模块与子模块，因而违反*通用接口原则*，进一步增加模块的复杂性并妨碍可互换性。

为了确保隔离、信息隐藏与可互换性，每个 Theseus 内核模块都被实现为一个独立的 Rust crate，其中包含一个 Rust module，随后被编译成一个与其他模块相互独立的二进制文件。我们并不把所有模块的二进制链接成一个可以直接、自由地访问彼此数据的单体目标文件，而是把每个二进制打包为最终操作系统镜像中的一个单独文件，使 *nano-core* 能够独立加载每个模块。因此，在保持尽可能小的前提下，Rust crate 是实体粒度（[12] 的 §3.1）的明确选择，也是模块隔离与替换的清晰边界。

### 3.2 无封装的状态管理

在 Theseus 中，依据*无封装原则*，模块摒弃传统的封装，转而把模块的状态（以及它与其他模块之间的进度概念）从其实体边界中解耦出来。在 S -> D 的交互之后，"服务器"实体 D 不是把与 S 交互进度的状态保存在自己内部，而是把该进度的密封表示返回给"客户"实体 S，从而 D 的内部状态不被改变。我们把这一技术称为*不透明导出（opaque exportation）*，因为它保留了信息隐藏（数据隐私）——这才是封装的真正好处。

不透明导出迫使客户（S）承担起维护其与服务器（D）交互进度的状态的责任。如图 2 所示，这与*无状态通信原则*相辅相成：在下一次调用 D 时，S 必须连同其参数一起提供 D 最新导出的进度，使 D 能够从上次中断之处继续，而无需在内部维护该进度状态。这让人联想到 CurlOS [16] 中的客户端状态存储，以及 RESTful Web 架构中的会话 cookie [13, 25]。

*【图 2：(a) 传统的基于封装的模块化会因为交互之后服务器中的状态溢出而造成客户-服务器纠缠。(b) 在 Theseus 中，服务器实体把进度状态不透明地导出给其客户，从而避免服务器中的状态溢出，实现无状态通信，并使客户与服务器相互解耦。（图略，见原 PDF 第 4 页）】*

尽管颠倒了封装，Theseus 的代码结构对开发者而言并不比现有的类 Unix 操作系统更复杂、更难理解。在源代码层面，数据结构与类型仍然和与之相关的函数一起放在一个模块中，但在运行时，这些状态存在于模块之外。开发者无需手工处理导出的状态，也无需把它们转移给其他模块；这些工作被抽象化并由编译器管理。乍看之下，无状态通信的开销似乎很高，但 Theseus 利用 Rust 中的仿射类型实现零拷贝通信 [9]，即使在相互隔离的实体之间也是如此，并且同时支持缓存与共享映射。Singularity 同样利用线性类型实现零拷贝传输 [22]，而 Theseus 能够把通信解析成一次函数调用，其开销低于 Singularity 的通道。

Theseus 必须应对在操作系统抽象的最底层不可避免存在的状态溢出。位于那一层的实体（例如帧分配器或中断处理程序）通常维护着与任何具体客户无关的系统级状态。然而，这些状态不得妨碍实体的可互换性。因此，当某个服务器实体同时持有与特定客户相关和无关的状态时，我们可以把该实体的状态划分为两部分：（i）一个与具体客户无关的最小状态表示，它以数据块（data blob）的形式被不透明地导出，在所有客户实体之间共享（联合所有权），或被放入一个指定的数据库；（ii）与特定客户相关的状态，表示服务器实体在为该客户服务时的进度，这些状态显然由该客户独占地拥有。我们预计这种两部分式的状态管理技术将有助于减轻此类实体中状态溢出的影响，从而保持其运行时可组合性。

### 3.3 纯软件的安全性与隔离

Theseus 利用 Rust 的内存安全保证来实现模块之间的数据隔离与故障隔离。它还实现了标准的基于内存管理单元（MMU）的虚拟地址空间隔离，原因有二：（i）为了证明以安全且运行时可组合的方式实现经典底层操作系统核心特性（如虚拟内存，而不仅仅是更高层的抽象）是可行的；（ii）证明限制用户态程序必须用 Rust 或其他安全语言来编写是不必要的。这一点与相关工作形成对比：后者放弃了基于硬件的隔离，转而用安全语言在软件中保证内存隔离，例如 SPIN [11]、Singularity [22]，以及较新的 Rust 工作 [27, 34]。

Theseus 通过三种技术实现模块之间的完全隔离，其开销与单体内核相近且非常小：私有模块命名空间、Rust 安全保证的一个变体，以及强制的健壮错误处理。首先，私有命名空间保证一个模块只能访问另一个模块的公共接口，而不能访问其内部数据。这正是强制把模块开发为相互独立的二进制（§3.1）所带来的好处——模块不可能命名其模块边界之外的数据，因为链接器无法解析这些名字。然而，尽管无法命名外部数据，模块仍然可以通过任意的指针操作访问那些数据，例如解引用任意地址或进行重解释转换，因为在单体内核中所有模块共享同一个堆。

其次，Theseus 利用 Rust 由编译器强制的内存安全保证来防止上述危险的内存行为。理想的方案是禁止在 Rust 中使用*所有* unsafe 代码块；然而，Theseus 不能简单地一刀切地禁止 unsafe 代码块，因为许多核心内核特性至少需要简短地使用一些 Rust 无法保证内存安全的指令，例如端口 I/O 与 MMIO、寄存器访问、中断配置等等。这些指令不会对模块隔离构成威胁，但在这个意义上说它们是 unsafe 的：它们可能使处理器崩溃，从而危及内存安全（而处理器一旦崩溃，内存安全也就无从谈起了）。因此，Theseus 通过一个编译器插件强制执行 Rust 安全保证的一个变体：允许这些指令，但*禁止所有其他 unsafe 代码*，以遵循最小特权原则。

第三，Theseus 强制每个模块*完全*处理来自其他模块的错误，并依据*统一接口原则*把错误显式地返回给它的*调用者*。所有公共模块接口函数都必须使用 Rust 的 `Option` 或 `Result` 类型来返回错误而不是 panic，这使得加固模块以抵御外部故障变得更加容易。通过禁止 Rust panic，Theseus 防止了一个模块中的语言级故障中止整个操作系统——那正是裸机 Rust 环境中默认的 panic 行为（见 §4）。

我们注意到，Theseus 无法使用现有的基于语言的隔离机制，因为它们只是通过对 unsafe 代码的全面限制来隔离内核*扩展* [11]，而核心内核特性恰恰需要 unsafe 代码。这包括 Singularity 中的软件隔离进程（Software-Isolated Process, SIP） [22]：它们的粒度比 Theseus 模块粗得多，并且不能包含任何 unsafe 代码，因而无法实现核心内核功能。其他非软件隔离方法，例如让模块运行在相互独立的地址空间中的微内核 [21]，以及 VINO 为每个 "graft" 模块提供专用堆与栈的做法 [40]，在面对数百个模块时会造成难以承受的开销。

### 3.4 惰性的、无状态的模块间通信

Theseus 中的模块间通信（Inter-Module Communication, IMC）在概念上类似于经典的 IPC，但具有不同的行为语义。每个模块把它的公共功能作为*已发布接口（published interface）*暴露出去，允许其他模块通过指向该接口的引用与之交互。接口引用通常会被解析为内核空间中的本地函数调用，但如果发生在硬件隔离的实体之间（例如用户态服务），也可能导致 RPC 风格的消息传递。对其他模块已发布接口的引用会在本地缓存为 Weak 指针，它们可能解引用到真实的接口端点，也可能不会；必须先把它们升级为 Strong 指针，然后才能解析并使用。缓存这些引用（以及一般意义上的缓存）在技术上构成了状态溢出，但这一点可以安全地忽略，因为被丢弃或失效的引用总是可以重新获取。这是状态溢出难以消除、但其纠缠的负面影响可以被完全缓解的一个例子。

如 §3.3 所述，Theseus 模块中的所有函数都必须处理并返回错误；我们利用这一点来只提供无连接的 IMC 协议，类似 UDP。显式的错误处理迫使更高层确保 IMC 消息被正确送达，这正是端到端论证 [39] 的一个应用。借用微服务文献 [28] 中的 API 术语来说，IMC 提供的是"聪明的端点，愚蠢的管道"。这与那些在编译/链接期就永久绑定在一起、因而能够静态保证函数可用性的系统形成了鲜明对比。

为了促进运行时可组合性，IMC 支持接口引用的惰性解析以及模块的惰性自动初始化。事实上，惰性求值是实现 Theseus 诸多目标的一般前提，因为模块可能在任意时刻发生改变或变得不可用。惰性接口解析使得模块可以随时独立于依赖它的模块被添加或移除。惰性初始化使每个新模块在第一次被访问时才初始化，并且它还可以惰性地初始化自己所依赖的那条模块链。那些不具有客户-服务器式软件调用者模型的模块（例如中断处理模块），可以指定由 nano-core 在加载时运行其初始化例程。

### 3.5 通用的、无状态溢出的操作系统模式

依据*基于模式的复用原则*，Theseus 提供了一个由通用、已知安全且无状态溢出的常见操作系统设计模式实现组成的库，它们可以在整个系统中复用，从而降低开发风险与繁琐程度。我们以往的工作识别了那些会造成或藏匿状态溢出的模式，例如多路复用器与分发器 [12]；我们计划把这类模式作为近期的优先工作。

Rust 提供了多种优秀的语言特性，Theseus 借助它们实现通用的无状态溢出模板。例如，由于 Rust 使用单态化（monomorphization）而不是类型擦除，Theseus 可以在编译期特化通用模式，而不增加任何运行时开销。另一个例子是 Rust 对高阶函数的支持，它使一个模式能够灵活地接受闭包，而这些闭包在一个确定安全且无状态溢出的环境中执行。

**示例：解耦的容错队列（DFQueue）**

我们通过实现 DFQueue 来展示可复用的、无状态溢出的模式的好处。DFQueue 是一个可泛型参数化的 MPSC 队列，它利用 Rust 的特性来防止状态溢出，*无论生产者或消费者的行为如何*。队列是实体间通信的关键构件，例如管道、FIFO、消息队列、信号；然而，标准的队列会造成状态溢出：生产者特有的数据被保存在消费者之中，使两个实体相互纠缠，并使生产者无法容忍消费者的故障。

通过利用 Rust 显式的所有权与借用语义，DFQueue 允许每个生产者保留其放入队列的数据的所有权，从而杜绝状态溢出。队列本身由消费者拥有，并且只包含指向生产者所拥有数据的借用引用，因此把它与每个生产者部分地解耦。我们用一个 `Completable` Rust trait 来增强入队的数据类型，它连同动态引用计数一起，使入队数据的生产者能够判断数据是否被成功处理，或者消费者是否发生了错误。消费者被禁止从队列中弹出数据，只能查看下一个条目、尝试处理它，并在成功之后把它标记为已完成。这种事务性语义完全解耦了生产者与消费者，并通过确保每个入队条目满足以下之一来实现容错：（i）在被列入出队计划之前已被成功处理；（ii）未被消费者完全处理，因此仍留在队列中；或者（iii）在消费者发生故障后从队列中丢失，但能够由拥有它的生产者重新入队。

此外，由于 DFQueue 构建在一个无锁且大体无等待的队列之上，它也可以安全地在中断上下文中使用。尽管我们最初未优化的 DFQueue 实现只达到 Rust 标准 MPSC 队列吞吐量的 37%，但其生产者侧的入队开销约为 85-110 个周期，即使在键盘中断处理程序中也完全可以接受。这一开销源自运行时引用计数，而在提供完成与失败状态这类保证时这是不可避免的；好在它并不妨碍 DFQueue 扩展到多个生产者线程。我们在 Theseus 中使用 DFQueue 的初步经验表明，Rust 是实现安全、通用且免于状态溢出的抽象与模式的明智选择。

## 4 用 Rust 开发操作系统的经验

在本文中，我们着重强调了使用 Rust 进行操作系统开发的诸多好处，包括内存安全、错误处理、所有权与借用语义、显式生命周期、高阶函数、仿射类型以及单态化。由于以往的工作已经评估过在操作系统内核中使用 Rust 的一些优缺点 [26, 27]，我们将基于开发 Theseus 的初步经验，讨论另一组关于 Rust 的值得注意的细节。

总体而言，我们发现 Rust 让编写操作系统变得更方便、更愉快，更不用说它更不容易出错。与系统编程的事实语言 C 相比，Rust 提供了高层得多的语言特性，例如强类型与类型推断、trait 与其他面向对象概念、lambda、表达式风格的语句以及其他函数式编程结构，所有这些都减少了实现工作量。此外，这些特性中的大多数可以在编译期得到保证，进一步加快开发过程，并有助于消除大多数并发与内存管理缺陷。

Theseus 大量使用类似*管程（monitor）*的数据结构：一种锁定机制封装了数据元素，并强制在访问内部数据之前先获取其锁。我们依赖 Rust 基于词法作用域的生命周期来保证，例如，保护某个元素的锁必须在该元素被访问与修改的整个期间一直被持有，并且保证在锁被释放之后，被锁住的元素不再可访问。我们意识到这并非 Rust 独有的特性（Java 和其他非 C 语言也提供管程），但 Rust 能够把管程的使用验证为*编译期不变量*，这对操作系统开发者来说格外有用：它把无法调试的数据竞争变成了直截了当的编译错误！

另一方面，Rust 也并非没有缺陷。其分配器 API 被限制为单一的全局分配器实例，使内核无法让 Rust 的集合类型从不同的内存池中分配。词法作用域并不完美：Rust 并不总是能正确推断前述数据守卫的隐式生命周期，从而产生令人困惑的编译错误，并迫使我们通过局部的名字重绑带来不便地延长生命周期。不过，Rust 还是一门年轻的语言，社区仍有潜力解决这些问题，希望未来的 Rust 系统实现能免于这些挫折。

我们遇到的另一个困难是（Rust 生态中）固有的偏好问题：开发者往往宁可 panic 也不返回错误；核心库与第三方 crate 中都充斥着 panic。如 §3.3 所述，Theseus 必须禁止内核空间中的 panic 调用，以防止某个模块中的故障拖垮整个操作系统。对于 Rust 库中我们无法修改的 panic，Theseus 必须关闭 Rust 的栈展开，以避免破坏调用栈上的全部状态，转而选择"panic 时中止（abort on panic）"这一不做任何处理的策略。一旦中止发生，我们手动地伪展开栈，回退到调用该库代码的栈帧，然后通过强制该帧向调用者返回一个代表该 panic 的 `Err` 或 `None` 值，从那一点继续执行。这之所以可行，是因为我们控制着 Theseus 中使用的调用约定，并且可以利用 Rust 基于模块的命名空间系统来确定应当从哪个栈帧恢复执行。Rust 的这一不足可以改进：鼓励开发者不要在简单的错误场景中习惯性地依赖 panic，或者为 no_std 的 panic 恢复提供可定制的支持。

## 5 相关工作

以往的系统工作用复杂的、临时拼凑的方案解决过 Theseus 的部分目标，包括在线更新与热替换 [5, 8, 20, 41]，以及故障隔离与容错 [21, 24, 43, 44]。语言层面的方法（例如 Erlang [7]）也在其运行时环境内实现了实体的热替换与容错。Theseus 的总体方法是：用一种独特的解耦策略彻底重新思考核心操作系统实体中的状态管理，并表明解决状态溢出这一底层问题，将有助于同时实现上述所有目标，而不只是其中之一。

与 Theseus 类似，近期的一些工作也用 Rust 实现了更安全的操作系统，例如 Tock [4] 与 Redox [3]，甚至提出了在 Rust 中实现经典内核抽象的方法 [27]。虽然 Theseus 从中获得了许多相同的好处，但其设计哲学以及无状态溢出与运行时可组合性这两大总体目标，与这些系统有着本质上的不同。

许多工作把可复用的组件或对象框架组合成操作系统，例如 Flux OSKit [19]、THINK [17] 和 Taligent [6]。由于它们的配置在编译期就被固定下来，这些工作并未考虑状态在不同组件之间传播的复杂性以及由此在运行时产生的纠缠。另一方面，Theseus 的 IMC 在组件化操作系统所使用的灵活通信接口（例如 Kni [38] 与 OpenCom [14]）的基础上加以扩展，以实现*通用接口原则*。

微服务架构 [28] 把庞大的单体应用拆分为许多运行在相互隔离的容器中的小型分布式组件，它受到了业界的广泛赞誉与采纳 [31, 37]。微服务在故障隔离、可维护性与可扩展性方面带来了改进 [32, 35]；虽然 Theseus 并非受微服务启发，但我们承认二者在动机与结构上的相似之处。然而，微服务本身并未解决状态溢出问题，而且它们针对隔离与通信的临时性解耦策略与机制依赖于底层操作系统基础设施，并在不同的业务部门之间差异巨大，几乎没有可以直接应用于 Theseus 的内容。

## 6 结语

本文确立了 Theseus——一个免于状态溢出的操作系统——的设计原则与高层实现细节。我们未来的工作包括完整实现上述计划，并证明 Theseus 在实现运行时可组合性与简化模块化操作系统演化方面的可行性。
