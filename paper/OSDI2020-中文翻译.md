## 摘要

本文描述一个名为 Theseus 的操作系统（OS）。Theseus 是多年实验的成果，其目标一是通过减少一个组件为另一个组件所持有的状态来重新设计并改进操作系统的模块化，二是利用安全编程语言——即 Rust——尽可能多地把操作系统的职责转移到编译器上。

Theseus 体现了两项主要贡献。第一，一种操作系统结构：大量边界清晰、且在运行时持续存在的微小组件相互交互，却不为彼此持有状态。第二，一种*语内*（intralingual）方法：利用语言级机制来实现操作系统本身，从而使编译器能够强制执行关于操作系统语义的不变量。

Theseus 的结构、语内设计与状态管理，以超出既有工作所能及的方式实现了核心操作系统组件的在线演化（live evolution）与故障恢复。

## 1 引言

我们报告一项在操作系统结构设计、状态管理与实现技术方面的实验，这些技术充分利用了现代安全系统编程语言（即 Rust）的能力。这项工作最初的动机是对*状态溢出*（state spill）[16] 的研究：一个软件组件由于处理来自另一个组件的交互而容纳了发生改变的状态，以至于它们未来的正确性取决于上述状态。状态溢出在现代系统软件中普遍存在，它导致原本模块化且相互隔离的组件之间产生命运共享（fate sharing），从而阻碍了诸如可演化性（evolvability）与可用性（availability）等理想计算目标的实现。

例如，Android 系统服务中的状态溢出会导致某个系统服务失效时整个用户态框架崩溃，丢失所有应用程序的状态与进度，甚至是那些并未使用该失效服务的应用 [16]。可靠的微内核（microkernel）也进一步证明，管理溢出到操作系统服务中的状态是容错 [21] 与在线更新 [28] 的障碍。

在可靠性必不可少的环境中，系统软件的可演化性与可用性至关重要。例如，在心脏起搏器 [26] 和空间探测器 [25, 62] 中，系统软件更新必须被一丝不苟地执行，做到不停机且不丢失执行上下文。即使在为可靠性而部署了冗余网络交换机的数据中心里，交换机软件故障与维护性更新仍会导致网络中断 [27, 48]。

为了探索在操作系统代码中能在多大程度上避免状态溢出，我们选择从零开始编写一个操作系统。我们之所以被 Rust 吸引，是因为它的所有权模型（ownership model）为实现两个组件之间的隔离与零成本状态转移提供了便利的机制。我们最初的操作系统构建经验带来了两点重要认识。第一，缓解状态溢出——或者说更一般地改进状态管理——需要重新思考操作系统结构，因为状态溢出（按定义）取决于操作系统是如何被模块化的。第二，Rust 这类现代系统编程语言不仅可以用来编写安全的操作系统代码，还可以静态地为操作系统行为确保某些正确性不变量。

我们这项实验的成果就是 Theseus 操作系统，它为系统软件的设计与实现做出了两项贡献。第一，Theseus 具有一种新颖的操作系统结构：由大量边界清晰、且在运行时持续存在的微小组件构成。系统维护关于这些组件的元数据并跟踪组件之间的相互依赖关系，从而为这些组件的在线演化与故障恢复提供便利（§3）。

第二，也是更重要的一点，Theseus 提出了*语内*（intralingual）操作系统设计方法，其要点是使操作系统的执行环境与其实现语言的运行时模型相匹配，并使用语言级机制来实现操作系统本身。通过语内设计，Theseus 使编译器能够把它的安全检查应用于操作系统代码，而对代码行为的理解不存在任何缺口；并将语义错误从运行时故障转变为编译期错误，这两者都达到了比现有操作系统更高的程度。语内设计超越了安全性本身，它使编译器能够静态检查操作系统的语义不变量，并承担一部分资源簿记职责。这一点将在 §4 中详细阐述。

Theseus 的结构与语内设计自然地减少了操作系统必须维护的状态，从而减少了其组件之间的状态溢出。我们在 §5 中描述 Theseus 进一步缓解状态溢出影响的状态管理技术。

为了展示 Theseus 设计的实用价值，我们在其中实现了在线演化与故障恢复（以提高可用性）（§6）。据此我们主张，Theseus 非常适合高端嵌入式系统与数据中心组件，在这些场景中需要在没有硬件冗余、或者在硬件冗余之外的情况下保证可用性。在这些领域，Theseus 作为新操作系统、需要安全语言程序等局限所造成的影响较小，因为应用程序可以在单一操作者控制的环境中与操作系统协同开发。

我们在 §7 中评估 Theseus 在多大程度上实现了这些目标。通过一组案例研究，我们展示 Theseus 能够轻松且任意地演化核心系统组件，其方式超出了以往在线更新工作所能及的范围，例如应用与内核的联合演化，或者微内核级别组件的演化。由于 Theseus 能够优雅地处理语言级故障（Rust 中的 panic），我们展示了 Theseus 容忍更具挑战性的、在操作系统核心中显现的瞬态硬件故障的能力。为此，我们给出了一项关于 Theseus 中故障显现与恢复的研究，并与 MINIX 3 就那些必然存在于微内核内部的组件的故障恢复进行了比较。尽管性能并不是 Theseus 的首要目标，我们发现它的语内设计与无溢出（spill-free）设计并没有带来明显的性能损失，但影响程度因子系统而异。

Theseus 目前实现于 x86_64 之上，支持大多数硬件特性，例如多核处理、抢占式多任务、SIMD 扩展、基础网络、磁盘 I/O 以及图形显示。它代表了大约四个人年的工作量，包含约 38000 行从零编写的 Rust 代码、900 行用于引导的汇编代码、246 个 crate（其中 176 个为第一方），以及分布在 21 个 crate 中的 72 个 unsafe 代码块或语句，其中大多数用于端口 I/O 或特殊寄存器访问。

然而，与商业系统相比，或者与 Singularity [33]、Barrelfish [8] 这类经历了更多开发的实验系统相比，Theseus 还远远不够完整。例如，Theseus 目前缺乏 POSIX 支持和完整的标准库。因此，我们不对操作系统的某些方面（例如效率或安全性）做出断言；本文聚焦于 Theseus 的结构与语内设计，以及由此为在线演化与故障恢复带来的收益。

Theseus 的代码与文档是开源的 [61]。

## 2 Rust 语言背景

Rust 编程语言 [40] 的设计目标是在编译期提供强大的类型与内存安全保证，它把高级托管语言的强大表现力与 C 语言般的效率结合在一起，同时没有垃圾回收或底层运行时。Theseus 利用 Rust 的众多特性来实现其语内、安全的操作系统设计，并采用 *crate* 这个 Rust 的项目容器与翻译单元来实现源码级的模块化。一个 crate 包含源代码和一个依赖清单。Theseus 并不使用 Rust 的标准库，但确实使用其基础核心 `core` 和 `alloc` 库。

Rust 的*所有权*（ownership）模型是其编译期内存安全与高效管理的关键。所有权基于亲和性（affinity），即一个值最多只能被使用一次。在 Rust 中，每个值都有一个所有者，例如，字符串值 `"hello!"` 被分配在 L4 就由变量 `hello` 所拥有。如果一个值被移动（moved），例如 `"hello!"` 在 L5 被从 `hello` 移动到 `owned_string`（L14），那么它的所有权（因此也即所有权者 `hello`）就不能再使用它。当所有者的作用域结束时，例如在一个词法块的末尾，被拥有的值就会被 *drop*（释放），这是编译器插入对其析构函数的调用来实现的。Rust 中的析构函数通过为给定类型实现 `Drop` trait 来体现，其中自定义的 *drop 处理器*（drop handler）可以执行任意操作，而不仅仅是释放内存。在上面的 L8，`hello_string` 离开了作用域并被自动释放（auto-deallocated）——它自己的 drop 处理器被调用。

值也可以被*借用*（borrowed）以获得对它们的引用（L6），并且这些引用的生命周期不能长于被拥有值的生命周期。L11 中的语法 `&'a str` 给出了 `'a` 这个名字，它是输入参数 `str` 的生命周期，并指明返回的 `&str` 引用具有与 `'a` 相同的生命周期。返回的 `&str` 引用在 L17 被赋值给 `hel`，这会在 L9 导致生命周期违规，因为 `hel` 会在 `after` 于 L8 被 drop 之后被使用（*after*）。Rust 的编译器包含一套借用检查器来强制执行这些生命周期规则，以及作为核心教义的*独占或可变*（aliasing XOR mutability）原则：对某个值可以存在多个不可变引用或单个可变引用，但不能两者兼有。这使它能够静态地确保栈上或静态值的内存安全。

Theseus 还广泛地利用 Rust 的 *trait*，它是一种抽象类型的声明，规定了该类型必须实现的方法集合，类似于面向对象语言中的多态接口（polymorphic interfaces）。Trait 可以用来作为泛型类型参数上的边界（bounds）。例如，函数 `fn print_str<T: Into<String>>(s: T) { }` 使用未命名 trait 边界来指定其参数必须是一个能够被转换为 `String` 的抽象类型 `T`。

```rust

 2      let hel: &str;
 3      {
 4          let hello = String::from("hello!");
 5          // "moved' error in L6
 6          let borrowed_str: &str = &hello;
 7          hel = substring(borrowed_str);
 8      }                       // --> lifetime error
 9      // print!("{}", hel);   //

11  fn substring<'a>(input_str: &'a str) -> &'a str {
12      &input_str[0..3]  // return value has lifetime 'a
13  }
14  fn consume(owned_string: String) { .. }
```

## 3 Theseus 概述与设计原则

Theseus 的总体设计规定了一种系统架构，它由许多被称为细胞（cell）的微小而独特的组件构成，这些组件可以在运行时被组合与交换。细胞是一种软件定义的模块化单元，其功能就像构成生物体中生物细胞那样（与 Rust 的 `std::cell` 无关），充当操作系统的构建基石。Theseus 使得所有用安全 Rust 编写的软件（包括应用程序和库）能够在单一地址空间（SAS）中与操作系统核心组件并存，并在单一特权级（SPL）上执行，依靠语言提供的类型与内存安全来实现隔离，而不是依靠硬件保护。本文所述的一切内容均以 Rust 编写，并在 SAS/SPL 环境中运行。

Theseus 遵循三条设计原则：

P1. 要求所有细胞都具有运行时持续存在的边界（runtime-persistent bounds）。

P2. 最大化语言与编译器的能力。

P3. 最小化细胞之间的状态溢出。

本节的其余部分描述 Theseus 如何满足第一条原则及其原因，而 §4 与 §5 分别讨论第二条与第三条原则。

### 3.1 运行时持续存在的细胞结构

Theseus 中细胞所具有的边界在实现时被清晰地定义，并贯穿整个运行时持续存在：一个细胞在实现时是一个 Rust *crate*，在编译时是一个目标文件，而在运行时则是一组已加载的内存区域（loaded memory region）以及按节（per-section）的边界与依赖元数据。这适用于*所有*细胞，而不仅仅是诸如整体式、安全语言操作系统或用户空间服务器中的内核扩展那类被挑选出来的子集：这些服务器中不存在针对组件的"基础内核"映像。清晰、可识别的细胞边界构成了 Theseus 中进行严格数据/故障隔离与状态管理的基石。

在运行时，Theseus 按需加载并链接所有细胞进入系统。简而言之，这需要找到并解析细胞目标文件、把它的各个节加载进内存、解析其依赖关系以写入链接器重定位条目、递归地加载任何缺失的细胞，并把新的公共符号加入符号表。这样做时，Theseus 会构建详细的*细胞元数据*（cell metadata），如*图 1* 所示，这对在线演化（§6.1）与故障恢复（§6.2）至关重要。已加载细胞的集合定义了一个细胞命名空间（CellNamespace），一个真正的命名空间，其中包含所有细胞的公共符号，用于快速解析细胞之间的依赖关系。每个已加载的细胞节点跟踪其组成的各个节以及它所拥有的内存区域（§4.3.1），这些节与该细胞目标文件中的节一一对应，例如可执行代码、只读数据和读写数据节。每个已加载节跟踪其大小、在内存中的位置以及双向依赖关系（传入与传出）；此外还存在其他元数据，用于加速细胞交换与其他系统功能。

*细胞边界的持久性降低复杂性*：Theseus 的持久细胞边界为操作系统结构中所有阶段的存在提供了一个一致的结构抽象。这降低了开发人员心智模型的复杂性，并简化了故障恢复与演化逻辑。Theseus 可以在运行时内省其自身的细胞，并从同样的以细胞为中心的视角管理它们。SAS/SPL 环境又以*完备性*（completeness）进一步增强了这一一致性视角：从最高层的应用程序与库，到核心内核组件，一切内容都是可观察的细胞。这使 Theseus 能够（i）实现一种统一适用于*任何*细胞的细胞交换机制，以及（ii）从多个系统层（例如应用程序与内核组件）以安全的方式联合演化细胞。

*以细胞粒度取得平衡*：Theseus 的细胞在作用域上是基本的（elementary）：我们倾向于把组件分离成微小的功能单元，直到它们之间出现无法接受的循环依赖，从而阻止进一步的分解。我们不使用 Rust 的多层模块层级结构，原因是一个 crate 包含多个 Rust 子模块（submodule），这些模块边界会在 crate 被构建为目标文件时丢失。相反，我们把本应成为模块的内容提取为不同的 crate，通过把各 crate 的源文件组织进 Theseus 仓库中的文件夹来实现层级结构。这种设计既提供了程序员友好的源代码层级视图，也提供了把所有细胞视为一组扁平的、互不相同的目标文件的简单系统视图。它还在需要交换无数微小细胞所带来的复杂性与交换大型整体化细胞所带来的低效和不灵活性之间取得了平衡。

### 3.2 用 `nano_core` 引导启动 Theseus

Theseus 把编译过程拆分到链接器阶段，把原始的目标文件直接放进操作系统映像中，使这种链接被推迟到运行时。从实际的角度来看，未链接的目标文件无法运行，因此我们必须跳跃式地启动 Theseus 的 `nano_core`。`nano_core` 是一组被静态链接在一起的小型、可执行的"基础内核"映像，仅由支持虚拟内存以及加载/链接目标文件所需的组件组成，它引导启动一个 bare-minimum 环境。由于静态链接会丢失它们的边界与依赖关系，`nano_core` 在最后一个引导阶段完全替代自身，动态地加载其组成的细胞，一次一个，使用在构建时固化到操作系统映像中的增强符号表和其他元数据。这满足了*所有*细胞都存在运行时持续边界的要求，从而允许 `nano_core` 在引导之后被安全地卸载。

## 4 赋予语言以权力

Theseus 遵循的第二条设计原则是发挥语言的力量，让编译器在最大可能的范围内检查安全性与正确性不变量。我们把这种方法称为*语内*（intralingual）设计（§3），因为它把 Theseus 的执行环境与该语言运行时模型的环境相匹配，并且完全在该语言的强类型系统所提供的语义之内实现操作系统语义。这类语内设计把编译器检查的不变量（例如不存在悬垂引用）扩展到*所有*类型的源，而不仅仅是语言内建的那些。

语内设计带来两大主要好处。第一，它使编译器能够承担操作系统的资源管理职责，减少了操作系统必须维护的状态，进而减少了状态溢出并加强隔离。第二，它使编译器能够在对代码行为的理解上毫无缺口地应用安全检查，接近于从应用程序到核心内核组件的端到端保证，并把语义运行时错误转变为编译期错误。

与此相对，传统的*语外*（extralingual）方法依赖硬件保护与运行时检查来维护安全、隔离与正确性。这些特性对编译器是透明的，并且需要 unsafe 代码。即使是现有的安全语言操作系统 [3, 13, 34, 44] 也存在缺口：语言级安全代码与底层的 unsafe 核心之间存在一个空白地带。下面我们描述 Theseus 如何弥合这个缺口，并把这类空白地带向编译器敞开。

### 4.1 与语言的运行时模型相匹配

许多语言（包括 Rust）的编译器都期望它的输出将成为一个可执行文件（或其一部分），并在单一地址空间与特权级中运行，例如单一用户空间进程。因此，编译器无法从整体上观察或检查独立编译组件的行为，因为这些组件运行在不同的地址空间或特权级中。

为了解决这一不足，我们定制了 Theseus 的操作系统执行环境，使其与 Rust 的运行时模型相匹配：（i）单一地址空间（SAS）存在，因此只有一组地址是可见的，对此 Theseus 保证一对一的虚拟到物理映射；（ii）所有代码在单一特权级（SPL）内执行，因此不存在其他执行世界或模式；（iii）只有一个分配器实例存在，与全局堆作为服务所有分配请求的唯一仲裁者的期望相匹配。注意，Theseus 并不支持单一任意堆内的多个分配堆（§7.3）。

### 4.2 语内操作系统设计

仅与语言的运行时模型相匹配，只能让编译器*看到*（view）所有 Theseus 组件。为了使编译器能够*理解*这些组件并把安全检查应用到它们身上，我们必须以一种能够把其安全需求、不变量与语义暴露给编译器的方式来实现它们。顺带一提，Theseus 在系统的所有层都尽可能充分地使用安全代码，始终把安全性置于其他方面（例如便利性、性能）之上。只有在从根本上不可避免的情况下才会进入 unsafe：执行直接位于硬件之上的指令，以及在 Rust 的基础库（即 `core` 和 `alloc`）中选择特定代码。

Theseus 超越了语言安全，进一步使编译器能够像检查内建不变量那样检查我们的自定义操作系统不变量。首先，对于每种操作系统资源，Theseus 都会识别出那组能够防止不安全且不正确使用的不变量。由于 Rust 编译器早已针对语言提供的类型与机制检查了无数不变量，Theseus 便利用这些既有机制，使其资源特定的不变量能够被*归并*（subsumed）进那些编译器不变量之中。例如，Theseus 使用 Rust 内置的引用类型，例如 `&T` 和 `Arc<T>`（Atomic Reference-Counted pointer），以安全、语言级的方式在多个任务之间共享资源（例如内存区域、通道端点），而不是像裸指针或把多个页映射到同一帧那样的语外共享机制。这通过把资源管理不当的检查吸收进编译器的生命周期不变量，消除了可能的释放后使用（use-after-free）错误。

其次，Theseus 对那些导出资源语义与内部函数（它们实现这些语义）的外部函数采用*无损接口*（lossless interfaces）。接口是无损的，如果跨越它时能够保留所有语言级上下文，例如对象的类型、生命周期、所有权或借用状态。此外，该语言级上下文的*来源*（provenance）必须是静态可确定的，使得编译器可以认证在调用链与接口穿越中不存在给定资源被使用的断裂环节。换句话说，语言级知识不能丢失、然后在语外被重新构建。例如，在 Linux 中调用系统调用会丢失其参数的类型与生命周期信息，因为它们必须被归约为原始整数值以跨越用户—内核边界。

*通过栈展开确保资源清洁*：我们强制执行的一个主要不变量，是使用默认的 Rust 安全性来防止*资源泄漏*（resource leakage），即已获取的资源未被释放且之后无法再被释放。尽管泄漏并不违反安全性，它通常是不正确的行为。Theseus 通过以下方式防止资源泄漏：（i）在 drop 处理器中实现所有清理语义，这是一种无损的语言级方法，让编译器独自确定何时触发资源清理；以及（ii）采用*栈展开*（stack unwinding）来确保已获取的资源在正常与异常执行中都总是被释放。

当任务在 Theseus 中获取资源时，它们直接拥有表示这些资源的对象（在它们的栈上 §5.1）。Rust 编译器静态地跟踪这些对象的所有权，从而静态地确定何时释放资源，因此在哪里插入其清理例程。只在 drop 处理器中实现所有资源清理，使开发人员不必承担考虑诸如异常控制流跳转这类特殊情况的复杂代码或纠正错误案例的负担。把这一方法应用于获取锁，使 Theseus 能够静态地防止许多死锁情况：锁守卫在栈展开期间被自动释放，并且域特定锁（例如修改任务使能表时的中断）在必要时会自动禁用。

我们在 Rust 中从零开始实现 Theseus 的 *unwinder*，其自定义展开逻辑基于 DWARF 标准 [1]，但不同于既有的展开库，它可以在没有标准库或分配的核心操作系统上下文中工作。Theseus 启动 unwinder 的唯一途径是软件或硬件异常，或者显式杀死某个任务的请求；它不会干扰正常的执行性能，这一点不同于垃圾回收器。这防止了失败的或非协作的任务危及资源释放与回收，从而加强了故障隔离。unwinder 使用编译器生成的信息以及细胞元数据来定位调用栈中的先前帧、计算并恢复该帧期间存在的寄存器值，并调用与发现清理例程。细胞元数据还使 unwinder 能够穿越非标准的栈帧，用于硬件引发的异步调用上下文，例如中断或 CPU 异常处理器。

Theseus 支持两种形式的语内资源吊销。首先，Theseus 可以通过杀死并展开一个不可协作的任务来强制吊销通用资源。这通过在任务关于安全资源访问的假设不再成立时避免执行代码，从而避免破坏性未定义行为。其次，Theseus 可以协作地吊销可回收资源，例如内存缓存与缓冲池，它们在自身类型定义中表达了资源存在的可能性，例如使用 `Option` 或弱引用。这种设计把系统级与语言级的资源动作统一起来，确保被吊销的资源被恰好一次地完全释放。

### 4.3 语内子系统的示例

下面我们描述 Theseus 如何以语内方式实现基础操作系统资源，即内存管理与任务管理。额外的细节（例如任务间通信（ITC）通道）以及其他不变量与示例可以在别处找到 [15]。

#### 4.3.1 内存管理

Theseus 通过*代码清单 2* 中的 `MappedPages` 类型以语内方式实现虚拟内存，该类型表示一个被静态保证连续映射到（可选地连续的）物理帧集合的虚拟页区域。`MappedPages` 是 Theseus 中映射与访问内存的根本性、唯一途径，并充当栈、堆以及任意内存区域（例如设备 MMIO 与已加载细胞）的底层表示。`MappedPages` 的设计以及编译器的类型系统强制执行以下关键不变量，它们把 Rust 的内存安全检查扩展到*所有*操作系统内存区域，而不仅仅是编译器已知的栈与堆。

*【代码清单 1：示例代码，映射一个表示 HPET 设备的内存区域，通过 MMIO 访问 HPET Vendor ID，然后派生一个新任务并通过通道把该内存区域发送给它。新任务接收该内存区域并用它来读取 HPET 计数器。此处引用的代码包含在清单 2 与清单 3 中。（清单略，见原 PDF 第 5 页）】*

*【代码清单 2：基本的 `MappedPages` 类型（L33）暴露了一个接口（L44-53），用于安全地访问其底层内存区域。`map()` 函数（L26）把一段虚拟页映射到物理帧，并返回一个表示该内存区域的新的 `MappedPages` 实例。为简洁起见，省略了合理性检查与细节。（清单略，见原 PDF 第 6 页）】*

*M.1：虚拟帧到物理帧的映射必须是一对一的，或者说双射的。* 这可以防止语言之下的别名（aliasing），迫使所有共享内存访问使用 Theseus 仅有的语言级机制，例如引用（`&MappedPages`）。在 Theseus 的 SAS 环境中（§4.1），这既是可能的，也不具有限制性。与此相对，既有与安全语言的操作系统设计允许不同的虚拟页映射到同一物理帧，这是一种语外方法，使共享对编译器而言透明且不可检查。

我们通过 `map()` 函数（L26）实现这一不变量，该函数利用类型安全来取得已分配页与帧的所有权，以便返回一个新的 `MappedPages` 对象。无损的 `map()` 接口静态地确保 `AllocatedFrames` 与 `AllocatedPages` 之间这一关系得以保持，保证它们不能被重复用于重复的映射。

*M.2：内存区域不得在其已映射区域的边界之外被访问。* 要访问一个内存区域，必须使用 `MappedPages` 方法，例如 `as_type()`（L45）或 `as_slice()`（L52），它们把一个静态大小的结构体或动态大小的切片覆盖在该区域之上；也存在可变版本，见下面的 M.4。边界内不变量（L46）会被动态检查，除非在大小或偏移为静态已知时被省略（例如某些 MMIO 情况）；这些访问函数返回保留了下文所述生命周期关系的尺寸化类型，因此是无损的。

*M.3：内存区域必须被恰好一次地解除映射；只有在不存在对它的未决引用之后。* `MappedPages` 以其 drop 处理器（L38）实现其解除映射（release）与清理语义，确保一个 `MappedPages` 对象（例如代码清单 1 的 L15 中的 `mp`）在正常执行（L18）与异常执行中都被解除映射。相应地，内存区域在其被解除映射之后不得再被访问。上述访问方法把被重类型化的借用引用 `&mut T` 的生命周期绑定到底层 `MappedPages` 内存区域的生命周期，允许编译器静态地阻止上述使用后释放的情况。否则，获得覆盖结构体的所有权但会无损地丢弃上述生命周期关系是不可能的。

*M.4：内存区域只有在按此方式映射时才必须是可变的或可执行的。* 我们提供专用的可变或可执行类型，`MappedPagesMut` 与 `MappedPagesExec`，它们分别提供 `as_type_mut()` 与 `as_function()`，静态地防止如别处所述 [15] 的页保护违规。

总之，`MappedPages` 弥合了编译器对内存的知识与操作系统的知识之间的语义缺口，在编译期阻止意外的无效页故障可能发生。注意，L49 中的 unsafe 代码是*无害的*（innocuous）（见 §8），因为它仅仅表明编译器无法确保覆盖结构体内容的有效性。结构体内容（例如代码清单 1 的 `HpetRegisters`）的正确性不可避免地留给开发人员。不管开发人员的错误如何，编译器仍然可以检查这个 unsafe 代码不会违反故障或数据隔离，因为其他不变量确保它不能产生悬垂引用（M.3）或访问超出 safe 代码可达范围的越界地址（M.2）。所有其他内存管理代码都是安全的，下溯到最底层，即页表遍历代码需要语外代码来适应硬件定义的页表格式的地方。

#### 4.3.2 任务管理

虽然 `MappedPages` 是语内内存管理的核心，Theseus 中的 `Task` 结构在内容与意义上都被最小化了。相反，任务管理围绕语内函数展开，这些函数利用一组一致的泛型类型参数来处理任务生命周期的每个阶段。

*【代码清单 3：派生任务的接口（L57）创建一个新的任务，并设置其栈，使得它在首次上下文切换时会跳转到 `task_wrapper()`，后者随后正常调用其入口函数。处理任务生命周期阶段的每个函数都用同一组 trait 边界（L54-56）参数化，确保任务的类型信息（函数、参数、返回类型）在其整个生命周期中被无损保留。为简洁起见，代码做了简化。（清单略，见原 PDF 第 6 页）】*

Theseus 的任务抽象在安全性上与 Rust 线程相似，并且是 Rust 线程的扩展。`spawn()` 接口（L57）要求指定入口函数 `F`、参数 `A` 与返回类型 `R` 的确切类型，并带有以下约束：（i）入口函数必须只能运行一次（L54 中的 `FnOnce`），（ii）参数与返回类型必须是可跨线程安全传递的（L55-56 中的 `Send`），以及（iii）上述三种类型必须比任务本身的生命周期更长久。因此，所有任务生命周期函数都是无损的，并且具有完全相同的类型参数（`F, A, R`），这允许编译器自然地把其安全保证扩展到跨多个 Theseus 任务的并发执行，并静态地防止类型无效的任务入口函数、参数与返回值。

*T.2：所有任务状态必须在所有可能的执行路径上被释放。* 释放任务状态需要除了简单地 drop 任务对象以防止资源泄漏（§4.2）之外的特别考虑。诸如栈之类的任务状态在展开期间被使用，只能在展开完成后被清理，而任务清理包含多个阶段，每个阶段允许不同程度的资源释放。例如，任务的栈与保存的寄存器上下文可以在它退出（L79）或被杀死（L82）时被释放，但其运行状态与退出值必须保留，直到它被 reap（未展示）。

此外，任务生命周期的结尾阶段存在多个潜在路径，每个路径都需要不同的清理动作。当任务运行完成时，其入口函数自然地把执行返回给 `task_wrapper`（L73），它可以安全地把任务标记为已退出，并带有其退出值。当任务崩溃时，异常处理器启动展开过程以释放所有任务持有的资源，之后它调用任务失败函数（L81），该函数把任务标记为崩溃。正常与异常执行路径都会调用一个最终的任务清理函数（L85），该函数从运行队列中移除任务并使其可被回收。所有这些函数都使用 `<F, A, R>` 类型进行参数化，这是语内故障恢复机制（例如可重启任务（§6.2））的关键部分。

*T.3：从任务的入口函数可传递到达的所有内存必须比该任务更长久。* 虽然 Theseus 中的所有内存区域都由 `MappedPages` 表示、并通过生命周期不变量防止释放后使用，但在 Rust 中难以用生命周期来充分表达任务与任意内存区域之间的关系。这是因为一个作为任务运行的 Rust 程序无法在其代码中指定：绑定到内存中对象的变量与底层 `MappedPages` 实例的生命周期绑定在一起，因为它们被栈、堆或程序段之类的抽象所遮蔽。即便可行，这也将是非常不优雅且不方便的，使得所有权毫无用处。例如，所有局部栈变量都需要被定义为带有从 `MappedPages` 所表示的栈派生出的生命周期的借用引用。

因此，为坚持这一不变量，我们转而建立一个所有权链：每个任务拥有包含其入口函数的细胞，并且该细胞拥有它所依赖的任何细胞，由细胞元数据中的按节依赖关系给出（§3.1）。因此，包含一个任务入口函数中所有函数与数据的可到达的 `MappedPages` 区域被保证比该任务本身更长久。这避免了把生命周期约束散布到所有程序变量上，并允许 Rust 代码按照标准假设正常编写：栈、堆、数据与文本节将总是存在的。

与此相对，传统的任务管理把这些不变量的强制执行留给操作系统程序员，是一种语外方法。在 Theseus 中，只有上下文切换期间对栈指针寄存器的修改不是语内的。

## 5 Theseus 中的状态管理

Theseus 遵循的第三条设计原则是最小化并理想地消除其细胞中的状态溢出。由于 Theseus 的组件结构基于细胞，状态溢出只会发生在交互中（例如函数调用），这种交互跨越细胞边界并导致接收细胞中的状态发生改变。

### 5.1 通过语内性实现不透明导出

Theseus 采用*不透明导出*（opaque exportation）来避免客户端—服务器交互中的状态溢出：每个客户端负责拥有表示其在服务器处的进度的状态，因此*导出*不能任意地把状态内省到或修改那个服务器私有的状态（这是类型安全的，因此是*不透明的*）。不透明导出之所以成为可能，是因为 Theseus 的语内设计能够把资源—进度簿记的负担从操作系统转移到客户端。这允许把状态分发或卸载到每个客户端，例如只在客户端任务的栈上持有。unwinder 仍然可以找到并调用清理例程，而不需要操作系统了解哪个客户端已经获取哪些资源，因此服务器与操作系统整体不需要维护每个客户端的状态。

与此相反，Theseus 摒弃传统的状态封装，其中服务器在客户端进度与资源使用之上持有所有状态 [16, 17]。这种封装构成状态溢出，并导致破坏隔离的命运共享：当服务器崩溃并丢失其状态时，其客户端也将失败。不透明导出仍然保留封装的主要好处，即*信息隐藏* [52]。

不透明导出的一个主要好处是*无状态通信*（例如 RESTful Web 架构 [24]），它规定对于给定请求应当被处理的所有内容都必须包含在该请求中。采用无状态通信的服务器不需要在成功的客户端交互之间存储中间状态，因为后续交互将是自给自足的，包含先前导出的状态。

不透明导出使 Theseus 能够避免常见的溢出抽象，例如句柄（handle）。服务器侧数据迫使服务器维护一个全局表，该表把每个客户端的句柄与其底层资源对象相关联，这是一种状态溢出。Theseus 拒绝句柄，转而支持客户端直接拥有底层资源对象，例如，一个应用任务拥有一个 `MappedPages` 对象而不是一个虚拟地址句柄，如代码清单 1 的 L4 中的 `mp` 所示。这使服务器（`mm` 细胞）从维护句柄表的负担中解脱出来，例如不必维护一个虚拟内存区域（VMA）列表，其中 VMA 对应于作为已映射区域句柄交给客户端的虚拟地址。注意，客户端只负责拥有（而非清理）那些表示其已获取资源的对象；当所述对象超出作用域时（或在展开期间），它会通过编译期插入的服务器提供的清理例程（即对象的 drop 处理器）得到清理。因此，Theseus 把拥有并持有状态的职责与实现并调用其清理功能的职责解耦。

*适应多客户端状态*：服务器定义的资源可能涉及或被不止一个客户端共享。因此，Theseus 扩展了不透明导出，以使*所有*相关客户端能够共同拥有该资源状态，即*多客户端状态*。所有权与资源共享可以以堆分配对象与自动引用计数（例如 `Arc`）来实现；虽然这可以被视为堆中的状态溢出，考虑溢出到分配器中并无用处，原因有二。第一，堆分配由被拥有的对象表示，它们指回堆，例如像 `Box` 或 `Arc` 这样的类型。因此，在观察堆中状态溢出发生的位置时，只需要考虑这些被拥有对象的传播就够了。第二，堆中的状态溢出不可避免：从创建一个新的本地字符串变量到调用函数的每个基本动作都会构成进入堆或栈的状态溢出，使其成为一个无用的度量。

### 5.2 Theseus 中特殊状态的管理

Theseus 细胞通常持有*软状态*（soft state），即那些可以丢失或丢弃而不出错的软状态 [19, 55]。软状态的存在是为了便利或性能，例如从硬件周期性读取的内存时钟源。尽管软状态在技术上确实构成状态溢出，它们可以被幂等地重新获取或重新计算，而对正确性没有影响。因此，Theseus 允许软状态在不影响演化或可用性的情况下利用状态溢出。

我们识别出两种一般形式的*不可避免状态*（unavoidable states）：（i）*无客户端*（clientless）状态，即硬件要求操作系统代表它维护的状态；（ii）处理那些不能提供足够上下文的异步、由硬件调用的入口点所需的状态。前者使不透明导出成为不可能，后者违反无状态通信。在第一种情况下，我们不能修改底层硬件的行为或容量以适应导出的状态。因此，Theseus 必须持有这些状态，以确保它们在整个执行过程中持续存在。例如包括低层 x86 结构，如全局描述符表（GDT）、任务状态段（TSS）与中断描述符表（IDT）。在第二种情况下，Theseus 必须存储必要的上下文，其生命周期超出异步硬件事件的入口函数，例如中断处理器。

为了在这两种情况下保持服务器细胞的可交换性（interchangeability），Theseus 把它们的状态指派给定义清晰的所有者细胞，例如 `state_db`，这是一个具有最小语义的状态存储设施，类似于键值数据库。任何单例细胞都可以把其状态移动到 `state_db`，并获得一个弱引用作为回报，这是一种软状态形式。尽管从其他细胞溢入了硬边界状态，`state_db` 仍保持可交换性，因为它独特地必须在自身的交换过程中予以配合，通过序列化到非易失性存储来加固自身。唯一另一个类似的细胞是细胞管理器（cell manager），它也必须序列化其细胞元数据。这种设计把硬件状态的生命周期与与之交互的服务器细胞的生命周期解耦，使所述细胞能够在不丢失强制性系统范围状态的情况下演化。

### 5.3 语内性与无溢出：示例

我们用两个示例子系统进一步说明语内性与状态无溢出设计之间的关系：内存与任务管理。

*内存管理*：Theseus 的 `MappedPages` 类型（§4.3）通过不透明导出消除状态溢出：请求映射的客户端拥有结果得到的 `MappedPages` 对象，例如代码清单 1 的 L4 中的 `mp`，而不是创建它的服务器（`mm` 细胞）。与此相对，现有操作系统中的 `mm` 实体容纳表示每个内存映射的状态溢出，例如虚拟内存区域（VMA）的列表或表对象；客户端必须盲目地信任底层映射与 VMA 在其虚拟地址句柄的使用期间持续存在。重要的是，我们把页表视为硬件要求的 MMU 状态，非常像 x86 的 GDT 或 TSS。在 Theseus 中，页表条目不是带有持久变量名绑定的语言级对象；因此，写一个页表条目是硬件外部化的副作用，而不是状态溢出。关键地，表示这一副作用的状态——从"未映射"到"已映射"的转变——不会丢失，而是反映在客户端拥有的 `MappedPages` 对象中，而不是隐藏的服务器侧状态改变。

*任务管理*：Theseus 的语内设计及其随后的不透明导出*显著地*减小了其 `Task` 结构的范围与大小，避免了大多数状态溢出实例从其他子系统进入其任务管理细胞。这是可能的，因为 unwinder 与编译器一起保留了完全清理任务已获取资源的能力，即使那些跨任务共享的资源，也不需要咨询其任务结构或资源簿记状态。Theseus 还把任务相关的状态（例如运行队列与调度器信息）移出任务结构，移入那些组成它们的组件。这种关注点分离比把庞大的操作系统状态列表囤积在任务结构中以便手动资源簿记、并把任务清理集中到一个包罗万象的任务结构中的传统操作系统更好。这种任务结构设计导致无数操作系统操作溢出到任务结构中，并导致紧密纠缠实体的横切依赖关系，阻碍它们的演化与恢复。因此，Theseus 的任务结构只能包含最基本必需品，例如，任务的运行状态、栈以及保存的执行上下文（寄存器值）。相应地，它排除了打开的文件、打开的套接字、内存映射、等待队列等的列表。

## 6 实现可演化性与可用性

为了展示 Theseus 设计的实用性，我们在操作系统内部实现了用于达成这些具有挑战性的计算目标的机制：在线演化与故障恢复。

### 6.1 通过细胞交换实现在线演化

Theseus 中的基础演化机制是*细胞交换*（cell swapping），这是一个多阶段过程，它用 `N` 个"新"细胞替换 `O` 个"旧"细胞；`O` 不必等于 `N`。首先，（i）Theseus 把所有新细胞加载进一个空的细胞命名空间（§3.1），这是一个隔离的链接环境。（ii）然后 Theseus 双向地验证依赖关系：新细胞必须满足原本由旧细胞所满足的既有依赖关系，而既有细胞必须满足新细胞的依赖关系。隔离式加载使得这一切可以在对运行中的系统进行侵入式更改之前发生。（iii）Theseus 把所有依赖旧细胞的细胞重定向为依赖相应的新细胞，这涉及重写它们的重定位条目与依赖元数据、更新栈上对旧细胞的引用，并在必要时转移状态。（iv）最后，Theseus 原子性地把旧细胞及其符号从细胞命名空间中移除，同时移入新细胞。

演化 Theseus 的一个运行中的实例就像提交到它的仓库一样简单，它会触发我们的构建服务器工具来重新编译 Theseus 并生成一个演化清单文件，指定哪些新细胞应该替换哪些旧细胞。维护者还可以选择哪些细胞要单独演化，而所有其他必须随之演化的细胞会自动包含在内，以确保一个格式良好的演化清单。

Theseus 的设计为细胞交换提供便利，并简化了静默期（quiescence）与状态转移这类已知的在线更新技术。在阶段（i），运行时细胞边界使 Theseus 的（动态）加载器能够确保一个细胞的各节不会与其他细胞的各节重叠或交错，允许每个细胞声明对其内存区域的唯一所有权，从而可以在阶段（i）中被干净地移除。（ii）动态加载也会产生精确的依赖信息，这是阶段（ii）和（iii）所需要的。

*Theseus 中细胞的无溢出设计简化了状态转移*：如前所述，不透明导出允许服务器细胞更容易地被交换，因为它在静默期内不需要在连续的客户端交互之间维护状态。无状态通信减少了给定函数对其他细胞的依赖，因为它通过参数接收必要的状态以及函数回调或闭包。总体而言，这加快了阶段（iii）中的依赖重写与状态转移步骤。

*细胞元数据加速细胞交换*。在阶段（ii），依赖验证相当于在 Theseus 的细胞命名空间符号映射中快速搜索完全限定的符号。在阶段（iii），Theseus 不需要扫描每个任务的栈来判断可达性；可达性通过跟踪元数据中的依赖链接即可轻易确定。编译期所有权语义使 Theseus 的细胞管理器能够在阶段（iii）中放心地移除旧细胞及其符号，而不必先检查它们在别处的使用情况，因为编译器已经确保：只有当一个被移除的旧细胞不再被任何其他细胞引用时，它才会被真正 drop 并卸载；这避免了在全部元数据上进行计算复杂度很高的图遍历。

Theseus 的语内设计扩展了演化一个数据结构在阶段（iii）中需要的*传输函数*（transfer functions）。我们允许并要求这些函数以语内方式实现，使用 Rust 的类型转换 trait，例如 `Into`。传输函数的生成正在进行中，因此 §7.1 中报告的结果使用手动编写的传输函数。

### 6.2 通过故障恢复实现可用性

下面我们描述 Theseus 如何从语言级异常（Rust panic）与硬件引发的异常（如 CPU 异常）中恢复。Theseus 采用一种多阶段、级联的故障恢复方法，采取越来越激烈的措施，直到恢复正常执行。一个系统范围的故障日志记录故障上下文（例如指令指针、当前任务）以及为了跟踪进度和避免重复故障循环而采取的恢复动作。

第一个恢复阶段是简单地容忍故障，方式是通过栈展开完全清理失败的任务。这种形式的故障隔离允许那些依赖于与失败任务共享的资源的其他任务继续运行。

第二个恢复阶段是重启失败任务的一个新实例。我们扩展现有的任务基础设施（*代码清单 3*），提供完全语内的*可重启任务*（restartable tasks）实现，其中派生接口进一步约束 `<F, A, R>` 类型参数，使编译器能够检查任务是格式良好的并且可以安全地重启。增强的 trait 边界是 `F: Fn(A) -> R + Clone` 和 `A: Send + Clone + 'static`，这要求整个入口函数可以被安全地执行多次（`F: Fn`，而不仅是 `FnOnce`），并且参数可以被安全地复制（`Clone`）。

最显著的恢复阶段使用细胞交换机制（§6.1）来用加载在不同内存位置的新鲜实例替换损坏的细胞。这解决了由于无效访问代码或文本节引起的故障，这些节已被损坏（例如由于硬件内存故障）。这代表了最简单的细胞交换可能情形，没有缺失的依赖关系，也不涉及对代码或数据类型的更改。因此，失败的任务被重启（如上所述），使它能够在新的细胞实例中成功执行。

值得注意的是，Theseus 的故障恢复机制只依赖很少的依赖项，使其能够在多个子系统失败的情况下容忍最低系统层的故障。每个细胞阶段的故障关键 TCB 组件如下：（i）失败任务状态的清理依赖于 unwinder，它只需要一个基本的执行环境来访问栈并调用函数；（ii）可重启任务依赖于任务派生；（iii）细胞替换依赖于目标文件解析、加载与链接。所有这些都可以在 Theseus 中 CPU 异常处理器的上下文中安全地执行。与此相对，可靠微内核（如 MINIX 3 [30]）中的故障恢复方法需要上下文切换、中断、IPC 和用户空间都正常工作。

## 7 评估

我们评估 Theseus，以展示它实现了容易且任意的在线演化，并通过故障恢复提高系统可用性。我们评估语内的、无状态溢出（spill-free）设计对内存和任务管理性能的影响，并把 Theseus 的基准性能与 Linux 进行比较。所有实验均在 Intel NUC 6i7KYK [2] 上进行，该系统配备 4 个（8 SMT）2.6 GHz 核心和 32 GB 内存，除非另有说明。

### 7.1 在线演化

Theseus 的演化机制是*带内*（in-band）实现的，也就是说，在操作系统核心内部并使用其自身的特性，这与现有工作不同，现有工作在成熟的操作系统上实现带外（out-of-band）实时更新功能。因此，很难进行统计分析，展示哪些历史性组件可以被 Theseus 的实时演化支持。相反，我们使用案例研究（如 Baumann 等人 [9] 的做法）来证明 Theseus 能够以超越先前在线更新工作的独特方式演化系统组件。*图 2* 展示了三个案例研究的演化阶段的时间尺度：（a）ITC 通道，（b）调度器和运行队列基础设施，以及（c）以太网驱动程序和网络更新客户端。

*任务间通信（ITC）通道*：我们展示了 Theseus 如何演化其 ITC 通道层（相当于 IPC），从一个既有的同步、无缓冲的会合（rendezvous）通道到一个新的异步缓冲通道。我们之所以选择这个，是因为 MINIX 3、seL4 和 QNX Neutrino 的历史揭示了在其微内核核心中显著、必要的演化，最显著的是从同步 IPC 增加或改变为异步 IPC [4, 22]，所有这些都需要标准重启来应用更改。在这里，Theseus 通过实时演化（i）一个必须在微内核内部实现的基础 OS 原语、（ii）一个需要依赖的用户空间与内核实体联合演化的内核 API，以及（iii）一个被广泛使用的组件，同时保留依赖它的那些实体的执行上下文，从而推进了技术前沿。

在这个实验中，我们派生了多个相互交换消息的应用程序，每个跨越多个同步通道，除了已经使用所述通道的系统任务（例如输入事件管理器）。然后，我们在消息仍在传输中时的随机点发出一个实时演化命令。由于 Theseus 可以独立地交换细胞而不依赖于执行上下文，它可以在不杀死运行中的应用程序的情况下把通道实现换掉，如图 2(a) 所示，通过减少中位停机时间到 385 μs 来提高可用性，因为它保留了应用程序的运行时进度，避免了多米诺效应，不需要重启多个其他依赖任务。

*调度器和运行队列子系统*：在这个实验中（图 2(b)），我们用一个新的基于优先级队列的运行队列，替换既有的轮转（round-robin）调度器与既有的基于双端队列的运行队列。与此同时，Theseus 运行多个不同优先级的任务来打印消息，从而展示任务执行顺序和频率在演化前后的可见差异。这展示了 Theseus 在运行时演化操作系统本身的模块化（通过更改多个细胞边界）和核心细胞的能力，许多其他细胞不可避免地依赖于它们。

乍一看，这似乎是微不足道的，因为现有操作系统已经可以在运行时切换多个调度器。关键的区别在于，Theseus 作为 OS 启动时并不包含*先验*（a priori）知识或对多调度器的带内支持，而现有操作系统需要调度器基础设施，具有预定义的通用接口来适应多个调度器策略。这展示了一个重要的好处：Theseus 中的子系统不需要特殊的设计或接口来支持给定组件的多个版本，例如像 `schedule()` 或 `task_switch()` 这样的函数可以不知晓多个调度器。相反，Theseus 组件可以依赖任意、带外的细胞交换机制来演化或灵活地在多个替代之间切换，从而形成一个更简单的设计。

*以太网驱动程序和网络更新客户端*：在这个实验中（图 2(c)），我们演化 Theseus 来修复不可靠的网络下载，涉及两个必须以类似方式一同演化的细胞：（i）位于网络栈之下的核心以太网驱动程序，以及（ii）Theseus 的演化客户端应用程序，它在网络栈之上与构建更新服务器交互。这展示了 Theseus 处理协调的、多部分演化的能力（如上述调度器案例），与之相对的是只触及一个驱动函数的小规模在线更新。新的以太网驱动程序修复了一个隐蔽的错误：由于为已接收数据包的环形缓冲区不正确地设置头指针与尾指针寄存器，它导致了不一致的连接性；新的演化客户端则修复了其 HTTP 层的用法，以便从意外的远端套接字断开中正确恢复。我们在不丢失任何 NIC 配置或数据包数据进度的情况下做到了这一点，测试方式是下载文件并用校验和加以验证。

这个案例表明，Theseus 可以提供*无冗余的可用性*（availability without redundancy），例如对于单独的嵌入式系统，以及在硬件冗余之上提供更好的可用性，例如对于在驱动程序更新期间必须停机的数据中心网络交换机。Theseus 可以执行"元演化"（meta-evolution），即加载一个新的演化客户端，再用该客户端自身的演化特性完成后续工作。这一过程得益于无状态溢出：网络状态由应用程序任务拥有，只有处理异步接收缓冲区所需的最小状态例外。

### 7.2 故障恢复

我们展示了 Theseus 在低级核心组件（例如那些必然存在于微内核内部的组件）中容忍故障的能力。我们专注于压力测试 Theseus 能否从语言之下的意外硬件引发故障中恢复；与之相比，Theseus 可以轻松地从语言级故障中恢复，因为编译器理解并能够考虑这些故障，保证栈展开会起作用。

我们的*故障注入*（fault injection）方法是在 QEMU 模拟器 [11] 上运行 Theseus，这使我们能够自动地对硬件状态做任意改变，包括随机翻转一个位或覆盖内存中的整个四字（quadword），以及随机递增指令指针寄存器以跳过指令。我们在运行图形渲染、任务派生、内存中文件系统访问与 ITC 通道使用等工作负载时注入故障，并监视工作负载/操作系统的行为，以确定故障是否表现以及如何表现。这遵循文献 [21, 30, 65] 中的常见做法。正如其他故障注入工作 [30] 所发现的，很少有随机注入的故障（<0.5%）会表现为可观察的失败；因此，我们增强故障注入器，使其针对内存中最可能表现故障的特定区域，即给定任务的栈、堆以及细胞内存（text、data、rodata 各节）的工作集。

*Theseus 从微内核级故障中恢复*：关于容错微内核的文献，例如 MINIX 3 [31] 和 CuriOS [21]，只评估从注入到用户空间系统服务器的故障中恢复，而不是微内核本身。为了展示 Theseus 支持从这类低级组件中的故障恢复，我们把故障同时注入 MINIX 3 的 IPC 层和 Theseus 的 ITC 通道，并评估我们恢复的能力。为了确保公平比较，我们手动检查了 MINIX 3 IPC 实现的所有层以及 Theseus 的 ITC 通道实现，以发现 13 个在两个系统中都导致确定性失败的故障 [45]。

在这 13 个故障中，Theseus 在除两个案例之外的所有案例中都正确恢复；其中接收者和发送者任务挂起但不崩溃；这可以通过超时或重置通道来解决。MINIX 3 在所有 13 个案例中都无法正确恢复；它在 11 个案例中内核崩溃，在其他两个案例中丢失消息。例如，损坏 IPC 接收例程中传递消息的指针在 Theseus 和 MINIX 3 中都表现为无效页故障；MINIX 3 的内核崩溃并重启，而 Theseus 优雅地重启 ITC 接收任务，允许发送者继续进行。

*一般故障恢复*：为了全面评估 Theseus 的故障恢复，我们向上述子系统中主动注入了 800,000 个故障，其中 0.083% 表现为可观察的失败。*表 1* 显示 Theseus 从所有表现出的故障中成功恢复了 69%。在 11% 的案例中，重启失败的任务就足以解决问题，这表明堆中存在损坏的栈值；在其余 89% 的案例中，Theseus 需要重新加载一个或多个细胞，这表明文本或数据节发生了损坏。Theseus 故障恢复机制的可观察停机时间在别处评估 [15]。

Theseus 在 31% 的表现出的故障中未能恢复，主要原因是 Rust/LLVM 缺乏异步展开（asynchronous unwinding）能力。编译器生成的是*同步*（synchronous）展开表，只覆盖那些可能发生语言级异常（Rust panic）的指令。由于硬件故障可以在任意指令处发生，Theseus 的 unwinder 在展开表中为发生故障的指令指针只能找到不精确的匹配，其清理例程可能不会完全释放在故障点获取的所有资源。注意，只有异常栈帧中的局部变量可能被遗漏；所有其他栈帧都得到了正确处理。虽然已知的异步展开方案在 Rust 中不受支持，我们正在探索操作系统与编译器层面的解决方案来增强展开信息的覆盖范围，这超出了本文的工作范围。

在其他 30 个案例中，故障导致系统或工作负载挂起，可以通过补充性的硬件机制（如看门狗定时器）予以恢复。在其余的 18 个和 62 个案例中，Theseus 未能重新加载一个新细胞来替换损坏的细胞，或者在 unwinder 自身的代码路径中遭受故障；对于这些情况，恢复失败是预期之中的。总的来说，这些代表了 Theseus 故障恢复的局限。

### 7.3 语内性与状态无溢出的成本

尽管性能不是 Theseus 的主要目标，其语内与无溢出设计自然会引发性能方面的疑问。总体而言，我们观察并预期这样一个趋势：许多无溢出设计只带来轻微开销，例如任务与堆管理，而另一些则表现更好，例如 `MappedPages`。我们比较 Theseus 的多个版本，以梳理出这些特定设计选择带来的性能影响。我们通过与 Linux 比较来进行评估：把 LMBench 微基准移植到 Rust，并在两者上运行它们；由于 Theseus 是实验性的且缺乏 POSIX 支持，结果应被视为*信息性的*而非结论性的。总体而言，我们没有发现任何明显的性能惩罚。

*MappedPages：更好的性能与可扩展性*：*图 3* 比较了 Theseus 的 `MappedPages` 设计与传统溢出式（spillful）内存映射实现，后者封装了一个传统的 VMA 红黑树，仔细建模 Linux 的行为。`MappedPages` 表现得略好，因为（i）客户端直接拥有 `MappedPages` 对象，这是一种分布式簿记，省去了在 VMA 树中搜索包含给定虚拟地址的内存区域的需要，以及（ii）内存安全不变量在编译期就得到保证。总体而言，这种差异不太可能显著影响真实系统工作负载。

## 8 局限性与讨论

*unsafe 代码是一种不可避免的必需品*：在需要与硬件交互的低级内核环境中，unsafe 代码是必不可少的，因为编译器缺乏对硬件语义的建模。并非所有 unsafe 代码都是等同的；我们区分两类 unsafe 代码：*无害的*（innocuous）与*传染性的*（infectious），其中传染性代码可能违反隔离，而无害代码不能。如果 unsafe 代码能够绕过类型系统去访问另一个组件内部的数据，从而"感染"该组件，例如解引用任意指针，那它就是传染性的；如果它只是访问可从 safe 代码可达的数据，例如把某个变量的地址写入一个 I/O 端口，那它就是无害的。无害代码仍然可能导致不正确的行为。作为正在进行的工作的一部分，我们开发了一个编译器插件，用来自动检查 unsafe 块中访问地址的可达性与类型安全；它目前支持语言级的 unsafe 块（例如 `MappedPages` 内部的），但需要手动把内联汇编（例如上下文切换例程）列入白名单。

*对安全语言的依赖*：Theseus 必须信任 Rust 编译器及其 `core`/`alloc` 库，在不出现可靠性漏洞（soundness holes）的前提下维护安全性。幸运的是，信任 Rust 的风险在不断降低，因为多项正在进行的工作正致力于通过检查 unsafe 的使用 [36, 37, 51] 来改进并验证 Rust 编译器及其基础库。要享受 Theseus 的好处，组件必须用安全 Rust 实现。其他安全或托管语言中的遗留代码可以通过用 Rust 实现其 VM/运行时来支持，但如果需要隔离，unsafe 语言则需要硬件保护，或者对内存访问进行动态插入（interposition）（类似 SFI [60]）。

*溢出式抽象*：在实现无溢出与支持那些需要或受益于状态溢出的既有抽象之间存在张力。一个例子是每个任务中表示其是否被阻塞的可运行状态。选择完全无溢出的实现会把这一状态完全移除，导致浪费 CPU 周期，因为任务别无选择，只能在等待不可用资源（例如已获取的锁）时无休止地自旋。由于这会影响性能与便利性，我们通过寻求折中来化解这一张力：把一个最小的布尔状态溢出到每个任务中，表示其可运行性。这避免了无意义自旋的高昂代价，但又不至于走到传统的完全溢出式设计——把关于是谁阻塞了它以及为什么（条件）的信息溢出到任务结构中。在 Theseus 中，被阻塞条件的状态存在于并且被阻塞该任务的每个实体所拥有，符合语内设计。

类似的张力也存在于其他子系统中，例如文件系统（FS）与内存。完全无溢出的文件系统会打破既有的 POSIX 接口，因为它把文件的唯一所有权授予当前访问它的客户端，这意味着在客户端释放它之前，该文件看起来是不存在的。我们尚未深入探索自定义文件系统，因此 Theseus 目前的折衷是支持遗留的文件系统标准，代价是接受文件系统细胞中的状态溢出。对于内存映射，Theseus 完全拥抱无溢出设计，即 `MappedPages`。

*语内性的局限*超越了由部分设计（§7.3）或运行时边界检查 [20] 所带来的开销。第一，把既有的 unsafe 组件或库集成进系统会破坏编译器知识的链条，也就是说，混入的语外性会限制其他语内组件的收益。第二，并非所有知识都能静态获得；对于非确定性的输入（例如用户指定的内存映射标志），运行时检查可能是必需的。第三，相比使用简单的运行时检查，使用类型系统来表达不变量需要额外的设计工作，尽管在那些运行时条件复杂、难以正确处理的操作系统场景中，这种方式很快就会显示出优势。

## 9 相关工作

Theseus 从许多先前工作中汲取灵感。与它使用*安全语言*（即 Rust）相关的是，大量先前工作在操作系统中使用安全语言：SPIN 中的 Modula-3 [13]、JX 中的 Java [29]、Singularity 中的 C# [33]、Tock [44] 与 Redox [3] 中的 Rust，以及 Biscuit 中的 Go [20]。许多近期工作专门利用 Rust 的安全性来实现高效的隔离 [42, 49, 51, 66]。Theseus 的语内设计方法（§4.2）超越了单纯使用安全语言，它使编译器能够把资源特定的不变量吸收进既有不变量之中，从而在更大程度上检查安全性与正确性。

Theseus 对*单一地址空间*与*单一特权级*的使用受到 SPIN [13] 与 Singularity [33] 的启发，但目的不同于性能：使操作系统的运行时模型与语言的运行时模型相匹配（§4.1）。

我们这项工作的动机是近期被诊断出的、由状态溢出 [16] 引起的系统软件问题，以及由此提出的无溢出操作系统的主张 [17]。其他工作则隐式地针对状态溢出的症状，例如 CuriOS [21] 表明在服务器进程中持有与客户端相关的状态会使故障恢复复杂化；CuriOS 把所述状态移入每个客户端的地址空间，并在交互期间把它们临时映射进给定服务器的地址空间；这提供了有效的隔离，但带来开销，并且只适用于微内核操作系统中的用户态服务器。Theseus 则使用类型与内存安全，在同一 SAS 与 SPL 内隔离客户端与服务器状态。

Theseus 采用动态加载来实现其细胞的*运行时持续边界*。动态加载在操作系统中很常见，用于支持内核可扩展性 [13, 30, 56, 64]，但只能加载新模块，例如驱动与扩展，让它们与一个大型、整体化、没有清晰运行时边界的内核并存（而非取代它）。Jacobsen 等人把一个微内核作为间接层嵌入 Linux 内核，把 Linux 分解为轻量级能力域（capability domain）[35]；这有助于隔离内核子系统，但无法演化或恢复它们。

*微内核操作系统* [21, 31, 41] 为运行在硬件隔离的用户态进程中的操作系统服务提供了持久边界。Genode [23] 是一个类似模块化的操作系统框架，它创建进程的层级树以实现强访问控制。这些操作系统结构使得通过重启进程来从服务故障中恢复或更新操作系统服务变得更容易，但沿粗粒度进程边界的模块化限制了它们演化核心微内核组件以及从中恢复的能力。此外，Theseus 更细粒度的组件使得硬件强制的进程边界变得不经济。

*系统软件的在线更新*已被广泛研究。许多工作把在线更新改造进 Linux 这类遗留操作系统 [6, 18, 39, 46, 54, 58, 63]。现有解决方案需要深厚的内核专业知识或繁琐的手工工作来生成或应用更新 [18, 46, 54]；一些方案由于间接层 [18, 32, 57] 或全系统检查点 [39] 而带来开销；另一些则无法更改内核 API、内部数据结构或非函数实体 [6, 54, 58]。总体而言，这些工作只针对小的、局部的安全补丁。与之相反，Theseus 凭借其全新的操作系统结构与无溢出设计，能够对核心内核组件、其模块化以及内核 API 施加大范围的演化性变更。

K42 [9, 10, 32, 57] 是一个面向对象的操作系统，它通过对象的热交换深入探索在线更新，类似于 Theseus 的细胞交换。与 Theseus 不同，K42 需要在所有对象之上建立一个统一的间接层，并且只能交换*对象*，不能交换 OOP 语言层之下的低层代码，例如异常处理或硬件交互。类似地，基于 MINIX 3 的微内核方案（如 PROTEOS [28]）能够为用户态服务器进程容纳复杂的系统更新。Theseus 建立在 PROTEOS 新颖的状态转移技术之上，但能够演化更细粒度的组件，包括微内核内部的那些组件。

*容错操作系统文献*涵盖了各种各样的方法，包括使用软件域来隔离驱动程序与部分操作系统子系统中的故障并从中恢复 [43, 59, 60]、微内核中操作系统服务进程之间的硬件隔离 [21, 31]，以及驱动程序 [38] 或操作系统服务 [30] 的检查点/恢复以加快恢复。Theseus 使用栈展开与可重启任务等语内机制，确保语言级安全假设与编译器提供的隔离不会被恢复动作破坏。Theseus 还区分恢复组件（细胞）与恢复执行上下文（任务），能够恢复并替换比进程更细粒度的组件，并利用新颖的状态管理技术来简化恢复逻辑。

### A.6 评估与预期结果

由于硬件与执行环境的差异，论文中给出的确切结果可能与在其他机器上复现的结果不同。不过，我们在评估中得出的相对性能趋势与结论应当成立。

#### A.6.1 在线演化案例研究

在这些案例研究（对应论文中的 §7.1 与*图 2*）中，我们从一个 Theseus 标准构建开始，把它演化成一个具有完全不同功能的不同版本。这一过程会按照由我们的构建工具生成的演化清单所指定的内容，下载一组修改过的 crate，然后使用 `upd` 应用程序把它们应用到运行中的系统上。这些实验既可以在一台宿主机上复现（由它运行我们的构建服务器，并在 QEMU 内运行一个虚拟化的 Theseus 实例），也可以使用两台具备网络访问能力的独立物理机（一台作为构建服务器，一台运行 Theseus）。我们提供了关于如何搭建并复现每个案例研究的详细说明，以及描述演化流程完成后预期新行为的截图。我们还解释了如何获得原始数值并计算*图 2* 中的度量；可以预期的一个总体趋势是：加载并链接 crate 目标文件的第一步耗时最长，而关键的第三、四步非常快，在几十微秒到几百微秒之间。

#### A.6.2 故障注入与恢复

在这个实验中，Theseus 运行在 QEMU 模拟器之上，我们把 GDB 附加到虚拟化的 Theseus 实例上，并通过修改内存以及指令指针寄存器等其他硬件组件的内容，用脚本向其中注入故障。我们提供了运行 §7.2 中所述两个示例工作负载的 Theseus 预构建映像：访问内存中文件系统，以及使用任务间通信通道。每个映像都附带一个脚本，用于向该映像中运行的工作负载所使用的系统组件注入故障。在实验结束时，每个脚本应当输出成功恢复与失败恢复的次数。我们还提供了一份完整的 CSV 表，列出我们自己的试验中注入的每一个故障及其结果。

#### A.6.3 IPC 故障比较

在这个实验中，我们比较注入 Theseus 的 ITC 通道与 MINIX 3 的 IPC 通道的 13 个确定性故障。一个描述每个故障的性质以及在 Theseus 与 MINIX 3 中观察到的预期响应的表格，在该实验文件夹的 README 中给出。正如该 README 所述，修改后的 MINIX 3 源代码可在 https://github.com/theseus-os/minix_osdi_ae 获取，其中为每个故障提供了一个独立分支，并说明了如何构建并运行两个系统以复现上述故障恢复行为。

#### A.6.4 `MappedPages` 的评估

这个实验测量映射、重映射与解除映射一个 4 KiB 页所需的时间，采用两种配置：使用 Theseus 中无状态溢出的语内 `MappedPages` 实现，以及使用基于 VMA 红黑树的传统溢出式方法（见*图 3*）。我们提供了一个与 QEMU 配合自动化使用的预构建映像，并附带一个多次运行该基准测试、解析结果并计算论文中所给统计数据的脚本。可以预期观察到与*图 3* 类似的趋势：`MappedPages` 方法在大量并发映射下的扩展性优于基于 VMA 的方法。

#### A.6.5 任务子系统中运行队列状态溢出的评估

这个实验测量把状态溢出从运行队列与调度器子系统移出任务子系统所带来的开销，即*图 4* 中测量的开销。我们提供了两个 Theseus 预构建映像（以及手动重建它们的说明）：一个使用我们标准的运行队列与任务状态无溢出实现，另一个采用带有大型有状态任务结构的传统溢出式方法。可以预期观察到与*图 4(a)* 类似的趋势：在无溢出版本中，简单地移除一个已退出的任务的开销大致随系统中运行队列总数线性增长，而溢出版本应保持恒定。更需要观察的趋势是*图 4(b)* 所示的趋势：运行队列—任务状态溢出的总体影响相对较小，因为派生任务的成本占据了主导，超过为移除已退出任务而搜索运行队列的成本。

#### A.6.6 堆微基准测试

在这个实验中，我们运行 *threadest* 与 *shbench* 微基准测试，以测量论文*表 2* 中给出的、在安全性与语内性程度上各不相同的三种堆分配器版本的性能。我们为每种配置提供预构建映像，并说明如何手动构建它们。总体而言，预期的趋势是：unsafe 堆最快，其次是部分安全堆，然后是安全堆；绝对运行时间可能变化，但相对开销应与论文保持相似。

#### A.6.7 LMBench 微基准测试

在这个实验中，我们把 LMBench 基准测试的核心子集移植到安全 Rust 代码，并在三种环境下比较它们的执行时间：作为 Linux 用户态应用、作为运行在动态加载版本 Theseus 之上的应用，以及作为运行在静态链接版本 Theseus 之上的应用，如*表 3* 所示。我们为 Theseus 的两种配置提供预构建映像，以及移植后的 LMBench 源代码，还有用于构建与运行它的脚本和说明。在这些微基准测试中，我们预期 Theseus 总体上快于 Linux，因为它的 SAS/SPL 设计避免了传统硬件保护系统（如 Linux）所强加的额外边界跨越（地址空间与特权级）。
